# Admission & Memory Governance

GPU device memory is the one resource a DataFusion session cannot pretend is
elastic. Nexus therefore treats **admission** — deciding when a query may start
native execution and how much device memory it is granted — as an engine
concept shared by both consumption modes:

- **Library mode:** you own the `SessionContext` and install Nexus through a
  process-scoped `NexusGpuBackend`.
- **Server mode:** the Flight SQL server lowers its env/TOML configuration onto
  the *same* backend policy. Env vars are a presentation layer, not a second
  admission implementation.

This page governs *runtime* resources. Whether a candidate lowers natively at
all — plan-shape admission — is a separate plan-time contract described in
[Native Lowering & Fallback](./native-lowering.mdx). The rest of this page is
the runtime contract: who owns the ledger, when admission happens, how grants
are sized, and which layer enforces what.

## Design rules

1. **One ledger per device, one owner per process.** The per-device
   `MemoryGovernor` is the sole authority on device-memory grants. Two
   accounting authorities on one device can jointly over-commit it, so the
   backend must be shared, never duplicated, across the sessions of one
   process.
2. **Admission is per query, not per plan fragment.** A physical plan may
   contain several native fragments; they share one admission slot and one
   grant, so a plan can never deadlock against itself.
3. **Byte-denominated grants plus a slot cap.** The grant band governs memory;
   `max_concurrent_queries` bounds stream and host-side fan-out. Throughput on
   TPC-H-class work saturates around three concurrent queries; beyond that only
   tail latency grows.
4. **No disk spill.** Work conservation comes from grant banding, admission
   backfill, and chunk-boundary re-planning in the adaptive lane — never from
   spilling operators.
5. **Capability is configuration, not load.** Whether a query *can* run
   natively depends only on the band's `min`. It must not depend on who else is
   running.

Flight SQL uses the same unit as embedded DataFusion sessions. `GetFlightInfo`
and prepared-statement creation may plan and issue a Flight ticket, but they do
not acquire a GPU slot. If the client never calls `DoGet`, no native admission
is consumed. The first native execution poll behind `DoGet` admits through the
plan ticket above; a CPU fallback plan never enters the GPU ledger.

:::warning[Admission failures are structured, not silent]
Queue overflow and admission timeouts surface as the same structured
`resource_exhausted`/`service_overloaded` taxonomy the server has always
emitted, converted to `DataFusionError` at the boundary. Nothing silently
downgrades an admitted query.
:::

## One owner: `NexusGpuBackend`

The backend wraps exactly one `QueryService` and is the object sessions share.
Multiple `SessionContext`s installed from one backend share the governor,
stream pools, and admission queue.

```rust
use datafusion::execution::SessionStateBuilder;
use datafusion::prelude::SessionContext;
use datafusion_nexus::prelude::*;

let backend = NexusGpuBackend::builder()
    .memory_policy(NexusMemoryPolicy::BoundedAuto {
        device_ordinals: vec![0],
        budget_fraction: None,          // default: capacity − headroom
    })
    .admission(
        NexusAdmissionPolicy::default()
            .with_max_concurrent_queries(2)
            .with_slot_guarantee(SlotGuarantee::GuaranteedMinimum),
    )
    .build()?;                          // rejects contradictions loudly

let state = backend.install_on(SessionStateBuilder::new())?.build();
let ctx = SessionContext::new_with_state(state);
```

`build()` validates the policy against the resolved devices: empty or
duplicated ordinals, fractions outside `(0, 1]`, `want < min`, zero queue or
timeout values, and `Unbounded` memory combined with admission are all
structured build errors, not runtime surprises.

Backend-managed sessions **freeze** the backend-owned native keys:
`SET datafusion_nexus.native.*` fails loudly instead of silently diverging from
the shared ledger. Configure those knobs on the builder. The request-scoped
`datafusion_nexus.request.*` namespace is exempt from that freeze because it
does not change backend policy; it can only request a per-statement grant inside
the already configured tenant band. Flight SQL does not expose those keys as
mutable session state; set server or tenant defaults for Flight workloads.

:::warning[Build one backend per process per device set]
The per-ordinal governor is claimed process-globally, and `GuaranteedMinimum`
claims are exclusive: with the default slot guarantee a second backend on the
same ordinal is rejected loudly at build time
(`shared_governor_guaranteed_minimum_conflict`; a mismatched budget fails as
`device_governor_capacity_conflict`). The claim frees only after the first
backend's last query handle drains, so a rebuild must drop the old backend
first. Two `Optimistic` backends may coexist on one ordinal — they then share
the byte ledger (each sees the other's grants) but not admission queues or
slot guarantees. In every case, share the one backend object instead of
building a second. The plain `with_cudf_native` path (no backend) keeps the
historical per-query-full-budget behavior and is only safe for one query at a
time.
:::

## Grant bands and slot guarantees

Each admitted query receives a grant inside the tenant band
`[min, want]`, resolved against device capacity:

| Setting | Default | Meaning |
| --- | --- | --- |
| `max_concurrent_queries` | 2 (library and server) | Admission slot cap; bounds streams, host decode fan-out, tail latency. |
| `grant.min` | 1/8 of capacity | Capability floor: the largest query guaranteed admissible regardless of load. |
| `grant.want` | Derived from slot guarantee and execution mode | Target grant when memory is available; explicit config always wins. |
| `slot_guarantee` | `GuaranteedMinimum` | See below. |
| `max_queued` | 64 × slots | Queue depth before `admission_queue_full`. |
| `wait_timeout` | 60 s | Bound on queued admission wait. |

Default `want` is derived after the backend resolves device count, capacity,
slot guarantee, and native pipeline mode:

| Slot guarantee × lane | Default `want` |
| --- | --- |
| `GuaranteedMinimum` × strict or adaptive | Full capacity. The runtime grant still reserves `min` for remaining slots, so a lone query receives `capacity − (remaining_slots · min)`. |
| `Optimistic` × adaptive | Full capacity; blocked waiters can trigger cooperative shrink at chunk boundaries. |
| `Optimistic` × strict | `capacity − ((ceil(max_concurrent_queries / device_count) − 1) · min)`, so a strict query does not hold the entire per-device budget while later arrivals wait. |

**`GuaranteedMinimum`** reserves `min` for every empty admission slot, so any
arriving query can always receive its floor immediately. This is deadlock-free
and latency-predictable, while the default full-capacity `want` lets a lone
query use the memory that is not reserved for future floors.

**`Optimistic`** deletes the empty-slot reservation: a lone query receives
`want.min(available)`, and a later arrival that cannot get `min` waits (bounded
by `wait_timeout`) while smaller queries backfill past it. Highest utilization;
admission latency for large queries becomes load-dependent.

On the 96 GB reference card with the defaults, `grant.min` is 12 GB. With two
GuaranteedMinimum slots, a lone query can receive roughly 84 GB because the
ledger reserves only the other slot's 12 GB floor. The slot default of 2 is the
measured sweet spot: it captured most of the saturation-throughput win on
TPC-H bursts with no capability cliff.

`NexusGpuBackend` and the server always pass an explicit resolved device
capacity into the `QueryService`. Direct `QueryService` callers that use
`QueryServiceTenantConfig::with_grant_range` must do the same by setting
`QueryServiceConfig::device_capacity_bytes`; the unset compatibility path is
only for fixed-slice tenants where `min == want`.

### Per-Statement Grant Requests

`datafusion_nexus.request.requested_grant_bytes` is a request-scoped preferred
grant override. The optimizer reads it when it mints the plan admission ticket;
all native fragments in that optimized plan share the same ask. Unset or
`none` uses the backend's tenant `want` — with one exception: for
graph-dominated plans the ticket ask is derived from the graph memory model
(edge-count and dtype evidence in the lowered plan), so a `cugraph_*` query no
longer asks for the whole card by default. An explicit
`requested_grant_bytes` always wins over the derived ask.

The key overrides only `want`, never `min`. The request must be greater than or
equal to the tenant `min`, less than or equal to the tenant `want`, and no larger
than device capacity. Values outside that range fail loudly during
query-service admission. They are not silently clamped, because a mistyped ask
would otherwise change concurrency behavior without evidence.

`datafusion_nexus.request.requested_grant_min_bytes` is the floor-side
companion: a request-scoped minimum grant inside the tenant band. Admission
either returns a grant at least that large or keeps the query queued (up to
`wait_timeout`) — it never admits a query into a grant the plan already knows
is fatal, which turns "wait, get a leftover grant, then die on the memory
gate" into "wait until enough memory is actually free". It is validated with
the same loud out-of-range rejection as the want-side key and does not change
the tenant band itself.

Small asks leave more grant room for backfill. Large asks reserve more up front
when the query is known to need it. Tune from evidence: per-query reports expose
`query_grant_bytes`, `reservation_live_peak_bytes`, reservation denials,
allocator high-water bytes, and retry counters.

### Strict and adaptive stay separate

The elastic behaviors — grow-on-release and cooperative chunk-boundary shrink —
exist **only in the adaptive lane**:

- **Strict** execution is gate-first: it snapshots its budget at admission and
  never grows or shrinks mid-query. Its evidence surface is the strict bounded
  contract report.
- **Adaptive** execution re-reads its grant at chunk boundaries. When another
  query's release frees memory, running adaptive grants may grow toward `want`
  (weighted by QoS). When a blocked admission cannot fit, running adaptive
  grants are asked to shrink toward `min`; the shrink is acknowledged
  cooperatively at the next chunk boundary and the query re-plans its remaining
  chunks under the smaller budget — reclamation without spill.

## What DataFusion's `MemoryPool` governs

Device admission is deliberately **not** expressed through DataFusion's
`MemoryPool`: `try_grow` is synchronous and non-blocking on tokio workers,
while admission must be able to queue and wait. The pool also has no query
identity, so grants and placement are inexpressible there.

The host side *is* bridged: `NativeCudfExec` registers a
`MemoryConsumer("NativeCudfExec[host-output]")` against the task's memory pool
and accounts the host Arrow batches it materializes for downstream CPU
operators. Hybrid plans therefore stay honest under
`RuntimeEnvBuilder::with_memory_limit`, and the accounting is free when the
default unbounded pool is installed. If you install a bounded DataFusion pool
alongside a backend, the pool governs host operators; device memory belongs to
the governor.

CPU fallback concurrency is bounded separately from GPU admission. The server
defaults to two concurrent fallback statements and a 30 s fallback wait timeout,
exposed as `NEXUS_SERVER_CPU_FALLBACK_MAX_CONCURRENT_STATEMENTS` and
`NEXUS_SERVER_CPU_FALLBACK_WAIT_TIMEOUT_MS`; set the timeout to `0` to wait
indefinitely. Library users opt in with
`CudfOptimizerConfig::with_cpu_fallback_max_concurrent_statements` and can set
`CudfOptimizerConfig::with_cpu_fallback_wait_timeout`; the library default is
indefinite waiting for embedder compatibility. Nested fallback execution with
the same DataFusion `TaskContext` reuses the ambient fallback permit, so a
fallback statement that internally collects another fallback-planned source does
not acquire the semaphore twice. The semaphore governs statements that remain
on DataFusion CPU operators. It does not reserve GPU memory, does not appear in
`QueryService` admission snapshots, and is deliberately not coupled to
`max_concurrent_queries`.

## Server configuration lowering

The server constructs the same backend from its config. Existing deployments
keep working; the new keys are additive:

| Env | TOML | Backend field |
| --- | --- | --- |
| `NEXUS_SERVER_MAX_CONCURRENT_QUERIES` (alias: `NEXUS_SERVER_MAX_IN_FLIGHT`) | `admission.max_concurrent_queries` | `max_concurrent_queries` (default 2) |
| `NEXUS_SERVER_ADMISSION_GRANT_MIN` | `admission.grant_min` | `grant.min` — fraction (`0.125`) or bytes |
| `NEXUS_SERVER_ADMISSION_GRANT_WANT` | `admission.grant_want` | `grant.want`; unset means policy-derived |
| `NEXUS_SERVER_ADMISSION_SLOT_GUARANTEE` | `admission.slot_guarantee` | `guaranteed_minimum` \| `optimistic` |
| `NEXUS_SERVER_ADMISSION_WAIT_TIMEOUT_MS` | `admission.wait_timeout_ms` | Query-service admission wait timeout; default 60 s |
| `NEXUS_SERVER_CPU_FALLBACK_MAX_CONCURRENT_STATEMENTS` | `fallback.max_concurrent_statements` | Host-side CPU fallback statement limit; default 2, `0` disables |
| `NEXUS_SERVER_CPU_FALLBACK_WAIT_TIMEOUT_MS` | `fallback.wait_timeout_ms` | CPU fallback semaphore wait timeout; default 30 s, `0` waits indefinitely |

Setting the alias and the primary key to different values is a startup error.
Explicit shares are spelled as decimals: `GRANT_WANT=1.0`, and
`GRANT_MIN=1.0` for one full-card floor (`0.5` for two, `0.25` for four).
Always include the decimal point: the share parser reads a bare integer such as
`1` as **bytes**, and rejects `1/2`-style strings. To preserve the earlier
half-cap default, set `NEXUS_SERVER_ADMISSION_GRANT_WANT=0.5` explicitly.

## Observability

Admission is a first-class report surface, consistent with the repo's
reports-not-printed-plans convention:

- **Per-query DataFusion metrics** on the native exec nodes:
  `admission_sequence`, `admission_wait_time`, `device_ordinal`,
  `query_grant_bytes`, `reservation_live_peak_bytes`,
  `reservation_denied_count`, `allocator_high_water_bytes`, `retry_count`,
  `retry_resource_exhausted_count`, and `retry_reservation_failure_count`, with
  `_observed` companions where absence is meaningful. The execution TSV report
  carries the same facts.
- **Library diagnostics** through the backend:
  `backend.query_service().admission_snapshot()` (queue depths, active
  queries, next tenant), `memory_governor_reports()` (per-grant rows,
  capacity, available bytes — a pool-shaped read surface), and
  `device_memory_failure_reports()` (failure-callback counters, trim retries,
  last failed allocation bytes, and the latest observed async-pool
  reserved/used counters). The underlying cudf-rs manager also exposes
  async-pool reserved/used counters and an explicit trim hook for operator
  diagnostics and administrative controls.
- **Server surface:** the same snapshots in server logs and the
  `GetAdmissionStats` Flight action, behind the standard server auth.

"Why was I queued and how big was my grant" is answerable from evidence, not
from log archaeology.

## Where the boundaries are

- **cuGraph:** graph SQL executes eagerly through table functions. The
  admission ticket is ambient per query: a `cugraph_*` call executing inside a
  natively rewritten plan joins that plan's ticket, and a standalone
  `cugraph_*` query — including its fallback-planned edge and predicate
  fragments — admits exactly once through its own. Standalone *bounded*
  sessions (no backend) refuse to execute native fragments inside a
  `cugraph_*` call — a loud structured error instead of a second full-budget
  ledger. Graph workspace memory follows the same governance contract as
  relational work: a runtime statistics probe on the resident edge frame
  (exact distinct vertices, plus degree evidence for the workspace-heavy
  algorithms) prices the graph stage, that ask is gated against the query's
  actual grant, and the stage then executes under a per-stream budget token
  charged to the query's grant arena — libcugraph workspace allocations
  included. A stage priced too low fails as a contained, retryable structured
  error on that one query instead of pressuring the shared pool, and graph
  reservation rows carry the measured statistics, `graph_peak_bytes`, and the
  model error ratio so pricing drift is visible in every report.
- **Capability-first admission is unchanged.** Admission grants memory
  *capacity*; it never re-introduces estimate-driven plan admission. Rejections
  stay local and structured (operator, expression, type, source, reservation
  contract).
- **The governor is the admission ledger.** It is the only authority that grants
  or refunds bytes. The native reservation arena mirrors the current grant and
  physically rejects over-limit allocations; keeping those two aligned is the
  invariant every elastic feature is measured against.
