# Design

Algeon adds GPU execution to a DataFusion session. DataFusion provides SQL,
catalogs and query planning; Algeon translates supported work into GPU
operations and returns Arrow record batches through the original interface.
These pages call that GPU path **native execution**.

## A query through the system {/* #how-a-query-runs */}

<QueryArchitecture />

The diagram follows a query selected for native execution. Its filters, joins
and aggregations operate on GPU columns. The CPU still plans the query,
reads metadata and submits work. Local files and object storage can supply
the input; a query attempt uses one GPU.

An embedded application and the Flight SQL server use the same execution
stack. The server adds a remote interface, authentication and session
management around it.

## Priorities {/* #priorities */}

The design serves one workload: many ad-hoc OLAP queries from an agent or an
analyst against a shared GPU, most of them revised after the first attempt.
Three decisions follow from it and recur across these pages.

- The engine owns the physical plan. The optimizer rule decides which
  candidates [lower to native execution](./native-lowering.mdx#selection-fallback-and-mixed-execution)
  and which fragments stay on DataFusion; a query author chooses algorithms
  and their options and nothing about partitions, pushdown or kernels.
- A failed attempt returns a structured error. Native failures stay typed
  across the DataFusion and Flight boundaries, and each carries
  [evidence for whether to retry](../integration/handling-errors.mdx#retry-and-recovery-are-evidence-based).
  Once GPU execution starts, nothing replays on the CPU.
- Admission protects the shared device. Each attempt is admitted against a
  per-device ledger and runs inside an
  [immutable grant](./admission.mdx#device-profiles-and-grants), and a
  query that exceeds its grant fails without taking memory from another.

Reducing the latency of a query that already answers in tens of
milliseconds is not among those decisions. Algeon also integrates with one
query engine. The adapter crate installs into a DataFusion session owned by
the host application, there is no Substrait input, and the Flight SQL server
is the same library behind a network interface. The module boundaries below
are organized around DataFusion above and the RAPIDS libraries below.

## Module boundaries {/* #crates-and-ownership */}

The intermediate representation (**IR**) describes sources, operations and
their dependencies. Ownership across the query crates is:

| Crate | Contracts it owns | Source directory |
| --- | --- | --- |
| `algeon-datafusion` | DataFusion-dependent lowering, execution wrappers and integration | `crates/algeon-datafusion` |
| `query-planning` | IR, optimizer, capability, proof, admission contracts and compiled pipeline | `crates/algeon-query-planning` |
| `query-runtime` | Attempt lifecycle, query service, device ledger, immutable grants, cache, observation and metrics | `crates/algeon-query-runtime` |
| `query-engine` | Native execution composition | `crates/algeon-query-engine` |

The adapter imports each query crate directly. The engine imports planning
and runtime; runtime imports planning. These three query crates have no
DataFusion dependency. Imports come from the crate that owns the item; query
crates do not re-export another crate's modules as a facade. Public adapter
signatures may use owner-crate types, with an adapter re-export for each exposed
type. The
[owner-type policy](https://github.com/algeon-dev/algeon/blob/main/.config/policies/public-api/algeon-datafusion-owner-types.tsv)
records that disposition.

Below them, the GPU component crates provide Rust APIs over NVIDIA's RAPIDS
libraries:

| Component | Work performed on the GPU |
| --- | --- |
| `cudf` | Parquet decoding and column operations, including joins and aggregation. |
| `cugraph` | Graph construction and algorithms such as PageRank. |
| `cuvs` | Vector search, clustering and dimensionality reduction. |
| `cuml` | Machine learning operations and forest inference. |

The adapter, runtime and engine call the components they need directly.
Component APIs bind operations to a CUDA stream and memory resource; native
RAPIDS libraries perform the work. Shared interop contracts preserve buffer
ownership across library boundaries.

Backend memory models belong to their component owners. IR, facts, schedules
and admission contracts remain backend neutral.
