# Design

Algeon adds native GPU execution to DataFusion sessions. DataFusion provides SQL
parsing, catalog management, and physical planning; Algeon lowers supported physical
subtrees into GPU operations and emits Arrow record batches. These pages refer to
that GPU path as **native execution**.

## A query through the system {/* #how-a-query-runs */}

<QueryArchitecture />

A native query executes filter, join, and aggregation kernels on GPU columns
while the CPU handles planning, metadata reads, and task submission. The host
application's Tokio runtime drives CPU coordination, while GPU kernels run on
dedicated per-device runtimes ([Runtimes and threads](#runtimes-and-threads)).
Each query attempt executes on one GPU. Embedded applications and the Flight SQL
server share this execution stack.

## Priorities {/* #priorities */}

The engine architecture follows three core constraints:

- The engine owns physical plan selection. The optimizer rule decides which
  candidates [lower to native execution](./native-lowering.mdx#selection-fallback-and-mixed-execution)
  and which fragments remain on DataFusion CPU execution.
- Failed attempts return structured errors. Native failures retain typed codes
  across DataFusion and Flight boundaries with
  [evidence for retry decisions](../integration/handling-errors.mdx#retry-and-recovery-are-evidence-based).
  GPU execution does not fall back to CPU replay once started.
- Admission bounds device memory. Each attempt receives an
  [immutable grant](./admission.mdx#device-profiles-and-grants) committed
  against the per-device ledger. Allocations exceeding the grant fail without
  reclaiming memory from concurrent attempts.

## Module boundaries {/* #crates-and-ownership */}

The intermediate representation (**IR**) describes sources, operations and
their dependencies. Ownership across the query crates is:

| Crate | Contracts it owns | Source directory |
| --- | --- | --- |
| `algeon-datafusion` | DataFusion-dependent lowering, execution wrappers and integration | `crates/algeon-datafusion` |
| `query-planning` | IR, optimizer, capability, proof, admission contracts and compiled pipeline | `crates/algeon-query-planning` |
| `query-runtime` | Attempt lifecycle, query service, device ledger, immutable grants, cache, observation and metrics | `crates/algeon-query-runtime` |
| `query-engine` | Native execution composition | `crates/algeon-query-engine` |

The adapter imports each query crate directly. The engine imports planning
and runtime. Runtime imports planning. These three query crates have no
DataFusion dependency. Imports come from the crate that owns the item.

Below them, the GPU component crates provide Rust APIs over NVIDIA's RAPIDS
libraries:

| Component | Work performed on the GPU |
| --- | --- |
| `cudf` | Parquet decoding and column operations, including joins and aggregation. |
| `cugraph` | Graph construction and algorithms such as PageRank. |
| `cuvs` | Vector search, clustering and dimensionality reduction. |
| `cuml` | Machine learning operations and forest inference. |

The adapter, runtime and engine call the components they need directly.
Component APIs bind operations to a CUDA stream and memory resource. Native
RAPIDS libraries perform the work. Shared interop contracts preserve buffer
ownership across library boundaries. The
[cuDF component README](https://github.com/algeon-dev/algeon/blob/main/components/cudf/README.md)
shows how one binding meets these rules: its layers, handle ownership, stream
provenance and memory domains.

## API documentation

`algeon-datafusion` is the application-facing Rust crate; the query and GPU
component crates, interop and build support are implementation dependencies
published with it. Visible adapter APIs, and the workspace-owned types they
expose, carry rustdoc at the defining item. The
[API documentation boundary](https://github.com/algeon-dev/algeon/blob/main/scripts/test-harness.md#api-documentation-boundary)
defines that scope, and the [documentation checks](../build/tests.md) enforce it.

## Runtimes and threads {/* #runtimes-and-threads */}

Three Tokio runtimes serve a query.

| Runtime | Created by | Threads | Work |
| --- | --- | --- | --- |
| Host | The application (`#[tokio::main]` in `algeon_server`) | The host's choice | Planning, admission waits, result streams |
| GPU pool, one per device | `GpuExecutionPool` at backend build | `worker_count` workers plus blocking-lane threads, named `algeon-gpu-{d}` | cuDF, cuGraph, cuVS and cuML calls |
| Object-store control | First query service in the process | Tokio default, named `algeon-object-store-control` | Footer and cache-fill fetches |

The library builds no host runtime. The host's runtime needs the time driver
for admission waits and deadlines. The pool uses Tokio as a fixed-width thread
pool that keeps synchronous GPU calls off the host runtime. A job is an `async`
block with a synchronous GPU body and holds its worker until the body returns.
Query execution jobs take at most `worker_count - 1` workers, which leaves one
for context setup and release cleanup. Chunk lane jobs and source reads use the
blocking lane of the same runtime.

A submission acquires a job-class permit immediately. If a class is saturated,
the service returns `service_overloaded`, making the admission envelope of a
placed attempt the sole bounded waiting point. A pool thread that must wait on an async primitive
parks in `block_until`, which polls under `unconstrained` because an exhausted
Tokio cooperative budget returns `Pending` without registering the waker. A
job submitted from inside the same pool runs inline. Host-side `spawn_blocking`
covers backend close, server shutdown drains, the query-stats lease and
password verification.
