# Native Lowering & Final Plans

This page covers the *plan-time* native boundary: how a DataFusion physical
plan candidate becomes a native `QueryPlan`, what happens when it is not
selected, and what evidence every decision leaves behind. Process-wide runtime admission
— immutable device grants, per-device attempt bounds, and device-memory governance — is a separate
contract described in [Admission & Memory Governance](./admission.mdx). The
architecture overview and layering rules live on the [Design](./index.mdx)
page.

## Relational acceleration path

Relational selection is whole-plan: Nexus evaluates one completed relational
physical candidate, selects it as a native replacement when its contract is
supported, or preserves the executable DataFusion baseline. It does not
recursively extract arbitrary relational subtrees into a new CPU/GPU plan.
That timing is deliberate: the physical plan already encodes aggregate mode,
partitioning, projection pushdown, join shape, sort requirements, and file scan
facts. Starting from a logical plan would duplicate DataFusion's physical
planner inside the adapter. cuGraph operations are separate, explicit GPU
islands with their own required boundary.

:::warning[Runtime failures do not replay]
Candidate selection is a planning-time boundary. If a relational candidate is
not selected, DataFusion keeps its executable baseline. An Iceberg candidate
that is not selected keeps the same wrapper's executable CPU delegate. Once
native execution or an explicit GPU island starts, runtime failures surface as
structured errors and metrics; Nexus does not replay that already-started work
on CPU.
:::

## Baseline preservation and final-plan requirements

Installing the native optimizer preserves the executable DataFusion baseline.
`NotSupported` and `NotSelectedByCost` are candidate outcomes, not planning
errors. Iceberg scans follow the same rule through their executable CPU
delegate. A caller that requires a DataFusion-CPU-free final plan configures a
final-plan requirement such as `NoDataFusionCpu`. Nexus plans once, classifies that exact
completed plan as `DataFusion`, `Native`, or `Mixed`, then either executes it
or returns terminal `Rejected` when the requirement is not satisfied.

## Session wiring

`with_nexus_native` installs three physical optimizer hooks. Only the final
rewrite is the public relational decision point, but the surrounding hooks are
part of the operable design.

| Hook | Position | Why it exists |
| --- | --- | --- |
| `datafusion_nexus_native_count_only` | Before DataFusion `aggregate_statistics` | Detect count-only shapes before DataFusion's statistics shortcut hides the native candidate. |
| `datafusion_nexus_native` | After DataFusion's default rules | Run final whole-plan relational candidate selection, lowering, and report capture while DataFusion can still validate the rewritten tree. |
| `datafusion_nexus_final_plan_requirement` | After native lowering, before `SanityCheckPlan` | Enforce the configured final plan disposition without treating an executable Iceberg wrapper as a non-executable leaf. |

:::warning[Public optimizer rule name]
The public rule name `datafusion_nexus_native` is also the deduplication key.
Do not rename it casually.
:::

## Plan-shape admission and execution evidence

Plan-shape admission decides whether a candidate lowers natively at all. It has
two layers. The adapter first normalizes and validates DataFusion physical
shapes, expressions, Arrow types, sources, and lowering contracts. Once that
produces a DataFusion-free `QueryPlan`, engine-side capability analysis does
capability-first admission for bounded and compiled execution. A native IR
candidate is not admitted because it matches a broad query family; it is
admitted because the required node, edge, invariant, and reservation contracts
are locally supported.

| Boundary | Code | Evidence developers should assert |
| --- | --- | --- |
| Adapter candidate selection | `src/native/normalize.rs`, `src/native/validate.rs`, `src/native/lowering/` | `PlanningReport` rows with `CandidateOutcome::Selected`, `NotSupported { capability_reason }`, or `NotSelectedByCost { cost_reason, evidence }`. |
| Engine capability analysis | `crates/nexus-query-engine/src/capability/entry.rs` | Per-node, edge, invariant, aggregate-strategy, and envelope-admission decisions. |
| Bounded controller execution | `crates/nexus-query-engine/src/runtime/query_service/`, `exec/bounded/` | Capability-first admission, a per-device immutable grant, and reservation evidence. |
| Runtime execution | `execute_query_plan` / `execute_query_plan_with_gpu_inputs` | `QueryMetrics`, DataFusion metrics, and native TSV reports, not printed plans. |

Adapter-side `NexusNativeExecutionConfig` stores the DataFusion-facing knobs and
builds the native `ExecutionContext` at the DataFusion/native boundary. The
engine context then owns execution-time memory control, boundary policy,
reservation, source scheduling, retry evidence, and any enabled resident-cache
capacity. Resident-cache capacity is an explicit per-device ledger allocation,
not a query-level execution option.

:::warning[One bounded-controller evidence model]
There is one capability-first bounded controller. Native reports expose its
concrete `capability_contract_rows` and `capability_compiled_graphs` evidence;
deleted adaptive row/counter families are not emitted. Do not add a second
decision path or treat an unsupported capability as an adapter-side estimate;
unresolved GPU capability gaps belong in `cudf-nexus` / `libcudf`.
:::

Aggregates follow the same rule: state must be explicit in the engine. AVG is
partial `SUM + COUNT`, final merge, then final projection; unsupported lookalikes
stay on the DataFusion baseline until their state semantics are modeled and tested.
