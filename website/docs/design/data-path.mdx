# From Parquet to GPU memory

A Parquet file contains compressed column pages plus metadata describing their
locations. A GPU query needs decoded columns in **VRAM**, the GPU's local
device memory. Between those representations, Algeon must select byte ranges,
read them and decode them. Host staging buffers occupy separate system RAM.

## Projection and scan pruning

<ParquetRead />

The scan can exclude data at several levels. A **row group** is a horizontal
slice of a Parquet file, with a separate column chunk for each field.

| Unit | How the scan is reduced |
| --- | --- |
| Files | Native lowering preserves the file set supplied by DataFusion's scan, including any upstream file or partition pruning. |
| Column chunks | Projection keeps columns needed by downstream operators and predicates. In the [grouped-sum example](./native-lowering.mdx#translate-the-work), `status` must still be read for the filter even though it is absent from the final output. |
| Row groups | Native lowering preserves explicit row-group selections and can use footer statistics, such as min/max and null counts, to exclude groups for supported predicates. Groups with insufficient evidence remain candidates. |
| Rows | Predicates evaluate the rows in retained groups, inside the reader when pushed down or in a GPU filter operator. This reduces rows passed onward after decoding. |

When a predicate is pushed into the cuDF reader, its statistics filter can
reduce row groups further. Supported equality predicates can also use Bloom
filters stored in the file. The predicate and available metadata determine
which stages apply. Footer pruning of `s3://` sources before admission is an
embedded-session setting, `AlgeonNativeExecutionConfig::with_lakehouse_footer_pruning`;
the Flight SQL server exposes no object-store configuration.

The host reads metadata to identify schema, row groups and column ranges.
Selected payload reaches GPU buffers through the cuDF datasource and KvikIO.
cuDF decompresses and decodes the retained column chunks. Parquet bytes on disk
and decoded columns can have very different sizes. A selective row predicate
can still require reading many bytes when metadata cannot exclude row groups.

Source-read observations report `pruning_input_row_groups`,
`row_groups_after_stats_filter` and `row_groups_after_bloom_filter` when the
reader supplies that evidence. Their starting count is already after the
caller's row-group selection. A missing stage count means it was not reported.
It does not mean zero groups survived. Compare these counts with output rows
to distinguish metadata pruning from row filtering.

## The transport depends on the source

<StorageRoutes />

### Local NVMe and compatibility mode

Local reads use KvikIO compatibility mode. KvikIO issues POSIX reads such as
`pread` into a pinned host **bounce buffer**, reused across chunks, then
copies the bytes to device memory. That copy crosses the host/device link
(PCIe in the diagram, [NVLink-C2C](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html)
on some CPU/GPU systems) into VRAM, and selecting fewer column pages reduces
both storage reads and that traffic.

Buffered POSIX reads can pass through the operating system's page cache.
Where enabled and supported, `O_DIRECT` bypasses that cache. The host staging
and GPU copy still belong to this compatibility path. Larger range reads
amortize syscall and submission overhead.
Source reads run as `SupervisedWorker` jobs on the blocking
lane of the GPU execution runtime, each backed by an attempt auxiliary
permit. A read issued from an execution lane runs inline on that
lane. Reads never wait for a permit, because the coordinator may hold every
permit through its own lanes. With none free, a required read runs inline on
the coordinator and a prefetch is skipped. None of these source read tasks
execute on the host runtime. A `max_source_reads_in_flight` above 1
enables prefetch.

KvikIO's settings are global to the process. Algeon's cuDF component applies
them once, while `AlgeonGpuBackend::build()` builds the backend and before any
source read runs. The server, library embedders and the benchmark binaries all
build their backend through that call. The defaults are compatibility mode
`ON` (also
[libcudf's default](https://github.com/algeon-dev/cudf/blob/algeon-26.08/cpp/src/io/utilities/config_utils.cpp#L19-L33)),
64 I/O threads and a 4 MiB task size. KvikIO's own variables
`KVIKIO_COMPAT_MODE`, `KVIKIO_NTHREADS` and `KVIKIO_TASK_SIZE` override their
fields; a field whose variable is unset keeps the Algeon default. Algeon has
no other name or TOML field for these settings. At startup the server logs one
`source I/O ready` line, and its `kvikio_compat_mode`, `kvikio_threads` and
`kvikio_task_size_bytes` fields give the effective values.

KvikIO splits a local read into tasks no larger than the task size and runs
them on its thread pool. A process has one such pool. Local `pread` tasks and
`s3://` range reads share it, as do all devices of a multi-GPU backend. Each
compatibility-mode task borrows a 16 MiB pinned bounce buffer from a separate
KvikIO buffer pool. With all threads busy, that buffer pool holds up to 16 MiB
per thread, or 1 GiB at the default 64 threads. KvikIO keeps the buffers for
later reads. The server releases them at shutdown, after the last source read
ends; a library process keeps them until it calls
`cudf::io::drain_kvikio_bounce_buffer_pools` or exits.

### GPUDirect Storage

With a suitable filesystem, driver and device configuration, KvikIO can use
cuFile and **GPUDirect Storage (GDS)**. Storage hardware transfers the payload
to GPU memory through **DMA**, direct memory access, avoiding the host payload
bounce buffer. CPU code still opens files and submits requests.

`AUTO` permits a POSIX fallback, and cuFile also has its own compatibility
mode. Small or unaligned requests may use alternate paths. An enabled setting
alone therefore does not establish that a read used direct DMA.
See [KvikIO's mode controls](https://docs.nvidia.com/kvikio/latest/runtime_settings/#compatibility-mode-kvikio-compat-mode)
and the [GDS overview](https://docs.nvidia.com/gpudirect-storage/overview-guide/).

### Object storage and libcurl

Algeon's native S3 datasource uses KvikIO HTTP range reads. They run as tasks
on the KvikIO thread pool shared with local reads. libcurl receives
chunks into host buffers. KvikIO accumulates them in pinned staging memory
and copies them to the GPU. The network receive buffer and pinned bounce
buffer have different roles, even though both occupy host memory. Footer reads
and cache fills for `s3://` sources run on a process-wide
`algeon-object-store-control` Tokio runtime, separate from the host and device
runtimes ([Runtimes and threads](./index.mdx#runtimes-and-threads)).

KvikIO's
[remote transfer implementation](https://github.com/rapidsai/kvikio/blob/0f6900f08c5a7ca150689e5454ae28562f875eec/cpp/src/remote_handle.cpp#L37-L133)
shows the host staging and device copy. An `s3://` URL does not imply RDMA or
GDS.

### cuObject and RDMA

[cuObject](https://docs.nvidia.com/gpudirect-storage/cuobject/) answers an S3
range `GET` by writing the payload into a registered destination buffer with
**RDMA**, remote direct memory access; when VRAM serves as the target
destination, libcurl buffers and pinned staging memory are bypassed entirely
along the payload path (represented by the dashed line in the diagram above).
It needs a ConnectX-5 or newer InfiniBand or
RoCE adapter on the client and NVIDIA's cuObject server library in the object
store. Algeon does not support it yet: its S3 datasource reads through KvikIO's
remote handle, which in the cuDF 26.08 build moves every remote payload over
HTTP ([roadmap](../reference/roadmap.md#longer-term)).

## Source and workspace {/* #lakehouse-and-workspace-boundary */}

Local and S3 Parquet are read-only sources. SQL views belong to the mutable
DataFusion workspace; creating a view does not rewrite a Parquet file or
materialize it on the GPU.
Iceberg sources are currently [unsupported](../integration/overview.mdx#iceberg-support).
