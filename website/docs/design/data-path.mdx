# From Parquet to GPU memory

Parquet scans identify column byte ranges, stage buffers, and decode data into
GPU VRAM using cuDF and KvikIO. Host staging buffers remain in system RAM.

## Projection and scan pruning

<ParquetRead />

Scans prune unneeded data across multiple granularities:

| Unit | How the scan is reduced |
| --- | --- |
| Files | Native lowering preserves the file set supplied by DataFusion's scan, including upstream partition pruning. |
| Column chunks | Projection keeps only columns referenced by downstream operators and predicates. |
| Row groups | Lowering evaluates footer statistics (min/max and null counts) and Bloom filters to prune row groups for supported predicates. |
| Rows | Predicates evaluate within the cuDF reader or a downstream GPU filter, reducing output rows. |

When a predicate is pushed into the cuDF reader, statistics filters reduce row
groups before decompression. Footer pruning of `s3://` sources before admission
is an embedded-session setting, `AlgeonNativeExecutionConfig::with_lakehouse_footer_pruning`;
Flight SQL server sessions do not expose object-store pruning options.

Source-read observations report `pruning_input_row_groups`,
`row_groups_after_stats_filter` and `row_groups_after_bloom_filter` when the
reader supplies pruning evidence. Compare these counts with `output_rows`
to distinguish metadata pruning from row filtering.

## Row groups, source chunks and I/O tasks

| Unit | Defined by | Size describes |
| --- | --- | --- |
| Parquet row group | The file writer | A set of rows stored as separate column chunks, with footer metadata |
| Source chunk | Algeon's source planner | Selected row groups from one file, grouped against a decoded-byte target and a row-group cap |
| KvikIO I/O task | The I/O layer | A range of stored bytes to read, bounded by `KVIKIO_TASK_SIZE` |

The planner can combine several row groups into one source chunk. Compatible
source chunks can then be batched into a reader call. The reader selects the
column byte ranges, and KvikIO divides reads into I/O tasks on its shared
pool. One source chunk can therefore require many I/O tasks. The
I/O task size controls the read subdivision; the source-chunk target still
comes from the query's memory policy.

Source sizing uses estimates of decoded columns because dictionary-encoded
strings can expand substantially during decoding. The
[native settings](../integration/configuration.mdx#native-settings) define
throughput grouping, byte targets and their overrides. Follow
[chunk execution](./gpu-execution.mdx#cuda-streams-and-dependencies) to see
how a query's grant constrains that planning.

## The transport depends on the source

<StorageRoutes />

### Local NVMe and compatibility mode

Local reads use KvikIO compatibility mode. KvikIO issues POSIX reads such as
`pread` into a pinned host **bounce buffer**, reused across chunks, then
copies the bytes to device memory. That copy crosses the host/device link
(PCIe in the diagram, [NVLink-C2C](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html)
on some CPU/GPU systems) into VRAM, and selecting fewer column pages reduces
both storage reads and that traffic.

Buffered POSIX reads can pass through the operating system's page cache.
Where enabled and supported, `O_DIRECT` bypasses that cache. The host staging
and GPU copy still belong to this compatibility path. Larger range reads
amortize syscall and submission overhead.
Source reads run as `SupervisedWorker` jobs on the blocking
lane of the GPU execution runtime, each backed by an attempt auxiliary
permit. A read issued from an execution lane executes inline on that
lane. When auxiliary permits are unavailable, a required read executes inline on
the coordinator while prefetch pauses. Source read tasks do not
execute on the host runtime. A `max_source_reads_in_flight` value above 1
enables prefetch.

KvikIO's settings are global to the process. Algeon's cuDF component applies
them once, while `AlgeonGpuBackend::build()` builds the backend and before any
source read runs. The server, library embedders and the benchmark binaries all
build their backend through that call. The defaults are compatibility mode
`ON` (also
[libcudf's default](https://github.com/algeon-dev/cudf/blob/algeon-26.08/cpp/src/io/utilities/config_utils.cpp#L19-L33)),
64 I/O threads and a 4 MiB task size. KvikIO's environment variables
`KVIKIO_COMPAT_MODE`, `KVIKIO_NTHREADS` and `KVIKIO_TASK_SIZE` override their
fields; a field whose variable is unset keeps the Algeon default. At startup the
server logs one `source I/O ready` line, and its `kvikio_compat_mode`,
`kvikio_threads` and `kvikio_task_size_bytes` fields give the effective values.

KvikIO splits a local read into tasks no larger than the task size and runs
them on its thread pool. A process has one such pool. Local `pread` tasks and
`s3://` range reads share it, as do all devices of a multi-GPU backend. Each
compatibility-mode task borrows a 16 MiB pinned bounce buffer from a separate
KvikIO buffer pool. With all threads busy, that buffer pool holds up to 16 MiB
per thread, or 1 GiB at the default 64 threads. KvikIO keeps the buffers for
later reads. The server releases them at shutdown, after the last source read
ends; a library process keeps them until it calls
`cudf::io::drain_kvikio_bounce_buffer_pools` or exits.

### GPUDirect Storage

With a suitable filesystem, driver and device configuration, KvikIO can use
cuFile and **GPUDirect Storage (GDS)**. Storage hardware transfers the payload
to GPU memory through **DMA**, direct memory access, avoiding the host payload
bounce buffer. CPU code still opens files and submits requests.

`AUTO` permits a POSIX fallback, and cuFile also has its own compatibility
mode. Small or unaligned requests may use alternate paths. An enabled setting
alone therefore does not establish that a read used direct DMA.
See [KvikIO's mode controls](https://docs.nvidia.com/kvikio/latest/runtime_settings/#compatibility-mode-kvikio-compat-mode)
and the [GDS overview](https://docs.nvidia.com/gpudirect-storage/overview-guide/).

### Object storage and libcurl

Algeon's native S3 datasource uses KvikIO HTTP range reads executed on the
shared thread pool. libcurl receives chunks into host memory; KvikIO stages
them in pinned memory before copying to device VRAM. Direct storage-to-VRAM
transfers via cuObject RDMA are not supported. Footer reads and cache fills
for `s3://` sources run on a process-wide `algeon-object-store-control` Tokio
runtime ([Runtimes and threads](./index.mdx#runtimes-and-threads)).

KvikIO's
[remote transfer implementation](https://github.com/rapidsai/kvikio/blob/0f6900f08c5a7ca150689e5454ae28562f875eec/cpp/src/remote_handle.cpp#L37-L133)
reflects this host staging and device copy sequence.

## Caches along the path {/* #caches */}

A first run of a query leaves state in four places, and each one covers a
different part of the next read.

- The OS page cache holds file pages from buffered `pread`. A hit skips the
  NVMe read; host staging, the device copy and decoding still run.
- Algeon's source chunk planner caches Parquet footer metadata within one
  planning pass. Each query plan reads footers again.
- Decoded local-Parquet sources and constructed graphs can stay on the device
  under `cache_cap_bytes` ([Admission settings](../integration/configuration.mdx#admission)).
  The default is `0`, so queries share nothing on the GPU unless a server sets
  a cap. See [Reuse in bounded servers](../cugraph/overview.mdx#reuse-in-bounded-servers)
  and [Completion and resident data](./admission.mdx#resident-handoff-and-release).
- The RMM memory resource pool and the KvikIO bounce buffer pool keep their
  allocations after a query. The next query reuses that memory and reads its
  own bytes into it.

The [benchmarks](../reference/benchmarks/index.mdx) page states which of
these layers held data for each published run.

## Source and workspace {/* #lakehouse-and-workspace-boundary */}

Local and S3 Parquet are read-only sources. SQL views belong to the mutable
DataFusion workspace; creating a view does not rewrite a Parquet file or
materialize it on the GPU.
