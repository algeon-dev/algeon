# Inside GPU execution

After decoding, the input is a collection of buffers in GPU VRAM. The engine runs
one compiled schedule for each native fragment, coordinated from one worker of
the device's GPU execution runtime
([Runtimes and threads](./index.mdx#runtimes-and-threads)). Its tasks call GPU
operations, retain the intermediate results still in use and release completed
resources.

## Columns and memory access

<ColumnLayout />

Fixed-width values sit next to one another within a column. Nullable columns
carry a validity bitmap; strings use offsets into a character buffer. A scan
over `amount` can read adjacent values without loading unrelated fields from
each row. Adjacent GPU threads can combine adjacent accesses into fewer memory
transactions, much as locality reduces cache-line traffic in CPU code.

Different operators create different access patterns and intermediate data:

| Operation | Memory access and temporary state |
| --- | --- |
| Filter | Evaluate a column predicate and gather selected rows. Reading input can greatly exceed the size of the result. |
| Hash join | Build a hash table from one input's keys, probe with the other input, then gather matching row pairs. Probes can touch scattered buckets. Duplicate keys can expand the result. |
| Grouped aggregate | Combine rows by key into group state, then merge partial state when input is chunked. More distinct keys require more state. |
| Sort / top-k | Compare and reorder values. Chunk candidates require a merge before they form a global result. |

These access patterns explain why a compressed file's size cannot stand in
for the query's VRAM demand. Decoded columns, operator state and output
can coexist. Column reads and intermediate writes also consume device-memory
bandwidth, even after input transfers over PCIe have completed.

## CUDA streams and dependencies

`CudaStream` identifies an ordered queue of GPU work, and work on separate
streams needs explicit completion dependencies before sharing results.

<StreamSchedule />

The coordinator is one `QueryExecution` job on one worker, and its tasks run on
the attempt's root stream. Expanded chunk work (aggregate chunks, join probes
and fused top-k candidates) goes to blocking-lane jobs. An execution **lane** is
one auxiliary permit, one leased stream and a derived context. Its width is
bounded by the minimum of `source_work_per_attempt`, the permits available at
launch, and the pending work items; any run allocated fewer than two lanes
executes inline on the coordinator. At the default `source_work_per_attempt` of 1, no run reaches
two lanes. The coordinator merges lane outputs in dispatch order under the
required SQL semantics. **A DataFusion CPU partition does not determine lane
ownership or width.** A lane's stream lease lasts for the whole run, while each
chunk job can land on any blocking-lane thread.

Related terms use the word lane in other senses.

- An attempt lane (`lane_count`, which equals `max_active_attempts`) is the
  identity slot an admitted attempt holds for its lifetime. See
  [Capacity and allocation](./admission.mdx#device-profiles-and-grants).
- An execution lane is the permit, stream and context described above.
- Chunk lane work is one blocking-lane job that runs on an execution lane.

Cross-stream dependencies use completion fences, such as CUDA events. The
consumer waits for the producer's work before reading its buffers, and
buffer ownership lasts through the final use. All lanes allocate inside
[one query memory cap](./admission.mdx).

## Relational data into GPU algorithms {/* #gpu-algorithms */}

A SQL table function can run cuGraph, cuVS or cuML inside a larger query.
cuDF columns supply edges or features; the algorithm returns columns for
subsequent filters, joins and aggregation. Format conversion and result
ownership determine which boundaries borrow buffers and which perform device
copies. See [GPU table functions](./gpu-table-functions.mdx) for a PageRank
example, the prepared-export lifetime and the differences between the three
libraries.

## Result egress and host synchronization {/* #result-egress */}

When a query fragment completes its relational and algorithmic stages,
execution reaches its terminal sink (`ResultSink::HostArrow` or a deferred host
batch cursor). The engine transfers the output column buffers from VRAM to host
memory, packaging them into Arrow `RecordBatch` instances for DataFusion.

<ResultEgress />

The device-to-host copy is queued on the execution stream after the upstream
kernels and starts once they complete.

The host runtime polls the DataFusion stream and awaits each pool job without
blocking a host worker. The first poll runs admission and the fragment's
schedule. Each chunk then takes one pool job, which sizes the chunk to at most
4 MiB of Arrow buffers, reserves that estimate from DataFusion's `MemoryPool`
(one live reservation per stream), enqueues the device-to-host copy and waits
in `cudaStreamSynchronize`. The wait holds the pool worker until the copy
completes. Algeon sets no CUDA device scheduling flag. Under the runtime
default, `cudaDeviceScheduleAuto`, the waiting thread spins on its CPU core
while the process has no more active CUDA contexts than logical processors,
and yields to other threads otherwise.

Once `cudaStreamSynchronize` returns, the worker wraps the host buffers into
Arrow arrays without another copy. The last chunk ends the result stream,
and the attempt [releases its grant](./admission.mdx#resident-handoff-and-release)
once no fragment is running.
