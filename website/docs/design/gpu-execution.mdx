# Inside GPU execution

The engine runs a compiled schedule for each native fragment, coordinated from
a worker thread in the device's GPU execution pool
([Runtimes and threads](./index.mdx#runtimes-and-threads)). Operators execute
GPU kernels on decoded columns in VRAM, retaining intermediate results until
downstream consumers finish.

## CUDA streams and dependencies

`CudaStream` identifies an ordered queue of GPU work. Work on separate
streams requires explicit completion dependencies before exchanging data.

<StreamSchedule />

The coordinator runs as a `QueryExecution` job on one pool worker, executing
root tasks on the attempt's root stream. Expanded chunk work (aggregate chunks,
join probes, and fused top-k candidates) executes on blocking-lane jobs. An
execution **lane** consists of one auxiliary permit, one leased CUDA stream, and
a derived context. Its width is bounded by `source_work_per_attempt`, available
permits, and pending work items; runs allocated fewer than two lanes execute
inline on the coordinator. At the default `source_work_per_attempt = 1`, chunk
work executes inline. The coordinator merges lane outputs in dispatch order
under the required SQL semantics; DataFusion CPU partitions do not dictate
lane allocation or stream width. A lane's stream lease remains held for the
entire run, while chunk jobs may execute on any blocking-lane thread.

Related terms distinguish lane scopes:

- An attempt lane (`lane_count`, which equals `max_active_attempts`) is the
  identity slot an admitted attempt holds for its lifetime ([Capacity and allocation](./admission.mdx#device-profiles-and-grants)).
- An execution lane is the permit, stream, and context described above.
- Chunk lane work is a blocking-lane job executing on an execution lane.

Cross-stream dependencies use completion fences such as CUDA events. Buffer
ownership lasts through final consumption, and all lanes allocate within
[one query memory cap](./admission.mdx). Within composed island executions,
shared execution scopes coordinate multi-reader lifecycles, retaining resident
handles until the final reader completes.

## Runtime dynamic filters

The compiled executor derives dynamic filters from the producer's complete
join build or aggregate group-key state. `max_build_rows` bounds the producer
rows admitted to this work. Exact membership payloads retain distinct non-null
keys in the attempt's query memory domain and share them across consumers and
chunks. Empty and dense range payloads retain no key column. cuDF orders
membership reads against the retained producer stream and retains completion
dependencies until consumption ends.

Route discovery places a consumer only on a join input whose unmatched rows
the join discards. Inner and semi joins discard them on both inputs. A left
outer, anti or mark join discards them on its right input alone; each left row
reaches the output, or the mark column, whether it matches or not. A
null-aware anti join reads the nulls and the emptiness of its right input and
takes no route on either input. Only single-key joins under
`NullsDoNotMatch` produce a key route. Native execution builds the right input
of every keyed left outer and mark join. Build-side selection may move a keyed
semi or anti join's build to its left input, and the route then reduces the
right input. A key route at a left outer or mark join, or at an anti join that
builds its right input, would consume the left input and is rejected as
`UnsupportedJoinShape`.

Integer bounds and distinct counts classify empty, dense range, small-IN-list
and larger exact keysets without copying the key column to the host. Resident
exact payload metadata carries the existing kind, count and range diagnostics;
host predicate helpers cannot apply that payload. A source route requiring
reader or row-group pruning downloads the distinct keys, retains the device
keyset for post-decode membership, and preserves the source pruning policy.
The large reader-only producer policy continues to derive a scalar range.
Producer key limits and consumer type bounds follow
[native lowering contracts](./native-lowering.mdx#selection-fallback-and-mixed-execution).

## Relational data into GPU algorithms {/* #gpu-algorithms */}

SQL table functions integrate cuGraph, cuVS, and cuML within queries. cuDF
columns supply input relations, and algorithm output columns feed downstream
relational operators. [GPU table functions](./gpu-table-functions.mdx) details
buffer ownership, zero-copy interop, and layout requirements across RAPIDS libraries.

## Result egress and host synchronization {/* #result-egress */}

When a query fragment completes its relational and algorithmic stages,
execution reaches its terminal sink (`ResultSink::HostArrow` or a deferred host
batch cursor). The engine transfers the output column buffers from VRAM to host
memory, packaging them into Arrow `RecordBatch` instances for DataFusion.

<ResultEgress />

The device-to-host copy is queued on the execution stream after the upstream
kernels and starts once they complete.

The host runtime polls the DataFusion stream and awaits each pool job without
blocking a host worker. The first poll runs admission and the fragment's
schedule. Each chunk then takes one pool job, which sizes the chunk to at most
4 MiB of Arrow buffers, reserves that estimate from DataFusion's `MemoryPool`
(one live reservation per stream), enqueues the device-to-host copy and waits
in `cudaStreamSynchronize`. The wait holds the pool worker until the copy
completes. Algeon sets no CUDA device scheduling flag. Under the runtime
default, `cudaDeviceScheduleAuto`, the waiting thread spins on its CPU core
while the process has no more active CUDA contexts than logical processors,
and yields to other threads otherwise.

Once `cudaStreamSynchronize` returns, the worker wraps the host buffers into
Arrow arrays without another copy. The last chunk ends the result stream,
and the attempt [releases its grant](./admission.mdx#resident-handoff-and-release)
once no fragment is running.
