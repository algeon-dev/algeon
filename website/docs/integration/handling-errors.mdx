# Handling Errors

Every Algeon-owned adapter failure carries a stable machine-readable `code`, a
coarse `kind`, and a `status` that says whether the condition is permanent,
temporary or persistent, beside a human-readable message. An application finds
that identity inside a `DataFusionError` or in Flight SQL gRPC metadata, and
should decide from those typed fields, never from formatted error text.
Ordinary DataFusion errors and transport errors below the server keep their
own policies; [Error ownership](../design/errors.mdx) covers how errors are
created and what each surface discloses.

~~~text
cuDF / cuGraph / cuVS
  -> shared native QueryError taxonomy
  -> algeon_datafusion::error::Error
  -> DataFusionError::External
  -> embedded application or Flight SQL status
~~~

## One identity, several projections {/* #one-identity-several-projections */}

| Field | Use |
| --- | --- |
| `code` | Most specific stable machine identity. |
| `kind` | Coarse grouping derived from `code`, for protocol and aggregate policy. |
| `status` | Coarse source condition derived from `code`: `Permanent`, `Temporary` or `Persistent`. |
| `operation` | Stable dotted identifier for the operation that added this boundary context. |
| `message` | Human diagnostic text. |
| `facts` | Structured diagnostic context, raw by default. |
| `source` | Original typed cause chain. |

Do not parse `Display` or `Debug` output, since adapter `Error::Display` emits
only the human message and native `QueryError` formatting can contain raw
facts and source text for trusted in-process use.

## Find the Algeon error {/* #crossing-datafusion */}

`From<Error> for DataFusionError` wraps the error once as
`DataFusionError::External`. DataFusion may add context, diagnostics, shared
errors or collections around it, and `find_algeon_error()` searches them:

```rust
use datafusion::common::DataFusionError;
use algeon_datafusion::error::DataFusionErrorExt;

fn record_failure(error: &DataFusionError) {
    if let Some(algeon) = error.find_algeon_error() {
        tracing::warn!(
            code = algeon.code().as_str(),
            kind = algeon.kind().as_str(),
            status = algeon.status().as_str(),
            operation = algeon.operation(),
            "Algeon query failed"
        );
        return;
    }

    tracing::warn!(error = %error, "DataFusion query failed");
}
```

The search walks source chains and each `DataFusionError::Collection` branch
in deterministic depth-first pre-order, bounded by depth and total node count,
and returns the first Algeon error it reaches, whatever its severity. A `None` result means only that
none was found within that budget; keep the application's existing DataFusion
policy then.

## Retry and recovery are evidence-based {/* #retry-and-recovery-are-evidence-based */}

`ErrorStatus` describes the source condition and grants no permission to retry:

| Status | Meaning |
| --- | --- |
| `Temporary` | The condition may clear, but the error alone does not prove when or how to retry. |
| `Persistent` | A dependency failure is known or observed to continue; stop automatic retry and escalate. |
| `Permanent` | Do not retry the same request automatically, since it normally needs different input, configuration, capability or code; cancellation is also terminal. |

There is no adapter `Error::is_retryable()`. To recover from an attempted query:

1. Classify the returned error with `QueryAdmissionOutcome::from_error` (or
   `from_error_with_queue_bounds`) while admission is still being attempted,
   and with `from_execution_error` after a handle has been published.
2. Retain the attempt completion the service published for the attempt.
3. Wait for the sealed `QueryAttemptReport`, read its `retry_advice`, and
   satisfy the advice's paired prerequisite before submitting a new attempt.

An execution error does not prove that cleanup finished; only the sealed
report binds the advice to completed cleanup. [Retry
evidence](../design/errors.mdx#retry-evidence) lists what the advice can say.

## Flight SQL status {/* #flight-sql-boundary */}

The built-in server looks for a typed adapter error first. An ordinary
DataFusion error gets a server-private classification for its gRPC code and
no public Algeon identity.

| Error kind | gRPC code | Client message |
| --- | --- | --- |
| `cancelled` | `CANCELLED` | The error message. |
| `not_found`, `permission_denied`, `unauthenticated` | `NOT_FOUND`, `PERMISSION_DENIED`, `UNAUTHENTICATED` | The error message, or fixed text for a source failure. |
| `planning`, `invalid_input` | `INVALID_ARGUMENT` | The error message. |
| `unsupported` | `UNIMPLEMENTED` | The error message. |
| `resource_exhausted` | `RESOURCE_EXHAUSTED` | Text naming the change the request needs. |
| `execution`, `dependency_failure`, `invariant_violation`, `internal` | `INTERNAL` | Static text pointing at `GetQueryStats`. |

- `invalid_configuration` has kind `invalid_input`. `algorithm_did_not_converge`
  returns `FAILED_PRECONDITION`.
- The static text refers to `GetQueryStats` for the query id in the status's
  `x-algeon-query-id` metadata. Every failure of a registered statement
  (`GetFlightInfo` planning, `DoGet`, `DoPut` updates, prepared statement
  actions) carries it; metadata RPCs such as `GetCatalogs` do not.

Every status built from an adapter `Error` carries `x-algeon-error-code`,
`x-algeon-error-kind`, `x-algeon-error-status` and `x-algeon-error-operation`,
followed by the [projected facts](../design/errors.mdx#projected-facts) that
apply.

The ADBC Flight SQL driver picks the Python exception class from the gRPC code
alone, and it maps `RESOURCE_EXHAUSTED` to `InternalError`. A memory-cap
failure therefore arrives as `InternalError` even though the server classified
it as `resource_exhausted`. Read `x-algeon-error-code` and `x-algeon-error-kind`
from the exception's `details` list of `(key, value)` pairs instead of
branching on the class.

### Memory failures {/* #memory-failures */}

For `query_memory_limit_exceeded`, `device_out_of_memory` and
`device_allocation_failed`, the message names the operation and the requested,
peak and grant bytes it carries, each also in GiB. It then asks the caller to
filter or project earlier, split the query, or raise
`admission.device_profiles.default_query_limit_bytes` for the device, since an
unchanged resubmission fails again. A device allocation failure also points at
the sealed attempt report.

| Fact | Meaning |
| --- | --- |
| `native_operation`, `budget_operation` | Code identifier of the failing operation. |
| `requested_allocation_bytes` | The allocation that failed. |
| `budget_peak_bytes` | The highest byte count recorded for the failing scope, including the failing operation's working set. |
| `budget_bytes` | The query grant. |
| `budget_current_bytes` | Usage sampled after the failing operation released its working set, kept out of the message. |

### Non-converged algorithms {/* #algorithm-did-not-converge */}

An `algorithm_did_not_converge` message names the algorithm, the iterations
reached and the configured limits, with matching `algorithm`, `iterations`, `max_iterations` and
`epsilon` metadata. Retrying unchanged repeats it. The message ends with the
native layer's `remedy`. Katz centrality asks for a lower `alpha` (below
1/lambda_max, the reciprocal of the largest adjacency eigenvalue) or a higher
`max_iterations`; HITS and eigenvector centrality ask for a higher
`max_iterations` or `epsilon`.

### Strict unsupported rejection {/* #strict-unsupported-rejection */}

In `native_required` mode, an unsupported column cannot stay on the
DataFusion plan. The code is `final_plan_requirement_unsatisfied`, Flight
returns `InvalidArgument`, and the message names the first blocking field in
schema order, its Arrow type and role:

~~~text
native_required mode rejected a plan that needs DataFusion CPU: GPU execution does not support projected column `countDetail` with Arrow type `List(Decimal128(10, 2))`
~~~

| Metadata key | Example value |
| --- | --- |
| `x-algeon-reason` | `unsupported_type` |
| `x-algeon-unsupported-column` | `countDetail` |
| `x-algeon-unsupported-column-type` | `List(Decimal128(10, 2))` |
| `x-algeon-unsupported-column-role` | `projected` |

`GetQueryStats` retains each as `fact.<name>`, such as
`fact.unsupported_column`. When the first blocker is some other
[plan element](../reference/gpu-coverage-report.mdx#what-blocked-a-candidate),
the message names it, or stays generic when the producing site cannot name one:

~~~text
native_required mode rejected a plan that needs DataFusion CPU: GPU execution does not support cast from Int64 to Int32 in `CAST(buys AS INT)`; EXPLAIN GPU lists every blocking candidate
~~~

That status carries `x-algeon-blocking-kind`, from a fixed vocabulary such as
`cast`, `aggregate_function` or `operator` (`column_type` for a column), and
`x-algeon-blocking-subject`, the text before the instruction. Each surface
carries these names under its own [disclosure rules](../design/errors.mdx#disclosure-model).

### Rejections in EXPLAIN GPU {/* #rejections-in-explain-gpu */}

[`EXPLAIN GPU`](./gpu-coverage-validation.mdx#rejected-statements) returns a
`rejected` summary row where execution returns a status. Its `reason_code` is
the `x-algeon-error-code` value, and `detail_json.detail` is the status message
without the trailing `EXPLAIN GPU` pointer or any `x-algeon-*` metadata. The
[rejected summary row](../reference/gpu-coverage-report.mdx#rejected-summary-row)
reference has the remaining rules.

## Query stats {/* #query-stats */}

`GetQueryStats` returns the retained diagnostics of one query as UTF-8 text.
Its action body is a plain string. The server first reads it as a query id. When
no query has that id, it reads it as a correlation id and picks the most
recently registered query with that id among the caller's own queries. The
response metadata carries the resolved `x-algeon-query-id`, and
`x-algeon-correlation-id` when the query has one.

A client that sets its own correlation id does not need to read any response
header. With the Python ADBC driver, set the header once for the connection:

```python
from adbc_driver_flightsql import dbapi

conn = dbapi.connect(
    uri="grpc://127.0.0.1:50051",
    db_kwargs={"adbc.flight.sql.rpc.call_header.x-algeon-correlation-id": "agent-run-1"},
)
```

The same key passed to `conn.adbc_connection.set_options(...)` changes the id
for later statements on that connection.

`GetQueryStatsSummary` takes the same body and returns only the `#` header
lines, the attempt labels and the trailer, without the planning and execution
records:

```python
import pyarrow.flight as flight

client = flight.FlightClient("grpc://127.0.0.1:50051")
results = client.do_action(flight.Action("GetQueryStatsSummary", b"agent-run-1"))
print(b"".join(result.body.to_pybytes() for result in results).decode())
```

~~~text
# algeon_datafusion_query_stats
# query_id=d09b7593-af81-4e40-a77a-39220a119fb8
# correlation_id=agent-run-1
# outcome=succeeded
# sealed=true
# elapsed_ms=1106
# sql=SELECT ...
# attempt_id=attempt-000000000000000886c3b4a7b7f0ef0a
# attempt_disposition=native
# attempt_outcome=succeeded
...
# incomplete=false
~~~

The summary answers whether the query finished, on which device, and whether
retry advice applies. Call `GetQueryStats` when the answer needs the per-operator
`[planning]` and `[execution]` rows, the `[structured_error]` facts or the
explained plans; a simple aggregate already returns a payload of more than
100 KB.
