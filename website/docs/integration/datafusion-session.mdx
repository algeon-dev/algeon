# DataFusion Session

Embed DataFusion Nexus when graph or GPU-accelerated SQL is one stage inside a
Rust service you already own. Your service keeps control of request handling,
auth, pooling, query construction, validation, and response formatting.

Add the dependencies with the features you need:

```toml
# Cargo.toml
[dependencies]
datafusion = "54"
datafusion-nexus = { version = "0.1", features = ["cugraph", "cuvs", "iceberg"] }
```

For production-style embedded use, build one process-scoped `NexusGpuBackend`
and install it on every `SessionStateBuilder` that should share GPU admission.
The backend owns the native QueryService queue, device-memory governor, stream
pools, and plan-scoped admission tickets.

```rust
use datafusion::execution::SessionStateBuilder;
use datafusion::prelude::{ParquetReadOptions, SessionContext};
use datafusion_nexus::{
    backend::NexusGpuBackend,
    graph_sql::CugraphSqlConfig,
};

async fn run() -> Result<(), Box<dyn std::error::Error + Send + Sync>> {
    let backend = NexusGpuBackend::builder().build()?;

    let state = backend
        .install_on_with_cugraph_sql(
            SessionStateBuilder::new().with_default_features(),
            CugraphSqlConfig::default(),
        )?
        .build();
    let ctx = SessionContext::new_with_state(state);

    ctx.register_parquet("edges", "edges.parquet", ParquetReadOptions::default())
        .await?;

    let df = ctx
        .sql("SELECT * FROM cugraph_pagerank('edges', 'src', 'dst')")
        .await?;
    df.show().await?;
    Ok(())
}
```

The default preserves the executable DataFusion baseline: a whole relational
candidate that is `NotSupported` or `NotSelectedByCost` remains executable on
DataFusion. To reject a completed plan that still contains DataFusion CPU
execution, use a final-plan requirement rather than a separate candidate
policy:

```rust
use datafusion_nexus::backend::NexusGpuBackend;

let backend = NexusGpuBackend::builder()
    .with_no_datafusion_cpu_requirement()
    .build()?;
```

Nexus plans once, evaluates that exact completed plan, and returns terminal
`Rejected` if the requirement is not satisfied. It never retries a native
runtime failure on CPU after execution has started.

## Host execution QoS

`HostExecutionQosConfig` is an independent outer statement bound. It wraps
completed DataFusion and mixed plans once, but not fully native plans, and it
does not consume a GPU query-service admission slot. Install it with the
session extension trait:

```rust
use std::{num::NonZeroUsize, time::Duration};

use datafusion::execution::SessionStateBuilder;
use datafusion_nexus::{
    backend::NexusGpuBackend,
    planner::HostExecutionQosConfig,
    session::NexusSessionStateBuilderExt,
};

let backend = NexusGpuBackend::builder().build()?;
let state = backend
    .install_on(SessionStateBuilder::new().with_default_features())?
    .with_host_execution_qos(
        HostExecutionQosConfig::new(NonZeroUsize::new(2).unwrap())
            .with_wait_timeout(Duration::from_secs(30)),
    )
    .build();
```

Use `Duration::ZERO` for an indefinite wait. To leave host execution
unbounded in an embedded session, do not install this rule.

`NexusGpuBackend::builder().build()` uses bounded device memory, two admitted
queries, `grant_min = 1/8`, a policy-derived `grant_want`, and
`SlotGuarantee::GuaranteedMinimum` by default. Sessions installed from the same
backend share one admission ledger; with the default guarantee, a lone query
can use the device budget that is not reserved for remaining slot floors.

For a complete multi-frontend service shape built on that same backend, see
the [Embedded Backend Example](./embedded-backend-example.mdx). It runs REST
pipelines and the built-in Flight SQL server in one process over a shared
`NexusGpuBackend` and `SessionContext`.

## Admission configuration

Tune admission on the builder, not on sessions. Backend-managed sessions
freeze the backend-owned native keys: a later
`SET datafusion_nexus.native.*` on a managed session fails loudly instead of
silently diverging from the shared ledger.

```rust
use std::time::Duration;

use datafusion_nexus::backend::{GrantBand, MemoryShare, NexusAdmissionPolicy, NexusGpuBackend};
use nexus_query_engine::runtime::SlotGuarantee;

let backend = NexusGpuBackend::builder()
    .admission(
        NexusAdmissionPolicy::default()
            .with_max_concurrent_queries(2)
            .with_grant_band(GrantBand {
                min: MemoryShare::Fraction(1.0 / 8.0),  // capability floor
                want: MemoryShare::Fraction(1.0),       // explicit full-capacity target
            })
            .with_slot_guarantee(SlotGuarantee::GuaranteedMinimum)
            .with_wait_timeout(Duration::from_secs(60)),
    )
    .build()?;
```

For per-statement sizing, use the request namespace instead of mutating backend
policy in embedded DataFusion sessions:

```sql
SET datafusion_nexus.request.requested_grant_bytes = '1073741824';
SET datafusion_nexus.request.requested_grant_min_bytes = '536870912';
SELECT ...;
SET datafusion_nexus.request.requested_grant_bytes = 'none';
SET datafusion_nexus.request.requested_grant_min_bytes = 'none';
```

`datafusion_nexus.request.requested_grant_bytes` is read when the optimizer
creates the plan ticket. It changes only the preferred grant for that optimized
statement; it does not change the tenant minimum, slot guarantee, queue limit, or
backend policy. `datafusion_nexus.request.requested_grant_min_bytes` is the
matching request-scoped floor: admission returns a grant at least that large or
keeps the statement queued until `wait_timeout`, instead of admitting it into a
leftover grant it would only fail on. Both values are allowed even on
backend-managed frozen sessions, but query-service admission rejects them if
they fall outside the tenant band (`grant_min`..`grant_want`) or exceed device
capacity. Flight SQL rejects
`SET datafusion_nexus.*` because request policy is lowered from server or tenant
defaults there, not mutable session state.

Two runtime behaviors to plan for in your service layer:

- **Admission is lazy and per query.** Planning admits nothing; the first
  native stream poll admits, and all native work in one plan shares one slot
  and one grant. Under load a query may wait up to `wait_timeout` for its
  grant; a full queue or an expired wait surfaces as a structured
  `service_overloaded` (`resource_exhausted`) error — treat it as retryable
  backpressure, not a query bug.
- **Build exactly one backend per process per device set.** With the default
  `GuaranteedMinimum` guarantee, a second backend on the same device is
  rejected loudly at build time
  (`shared_governor_guaranteed_minimum_conflict`), and the claim frees only
  after the first backend's last query handle drains. Two `Optimistic`
  backends may coexist but share only the byte ledger, not admission queues or
  slot guarantees. Share the one backend across every `SessionStateBuilder`
  instead.

Admission evidence for dashboards and debugging comes from the backend handle,
alongside the per-query `admission_*`, `query_grant_bytes`,
`reservation_live_peak_bytes`, allocator high-water, reservation-denial, and
retry metrics on the native execution nodes:

```rust
let queue = backend.query_service().admission_snapshot()?;
let governors = backend.query_service().memory_governor_reports()?;
let device_failures = backend.query_service().device_memory_failure_reports();
```

The model behind these knobs — plan-scoped tickets, grant bands, slot
guarantees, and the layered memory stack — is specified in
[Admission & Memory Governance](../design/admission.mdx).

## cuGraph SQL functions

`CugraphSqlConfig::default()` registers every supported `cugraph_*` function.
On a backend-managed session, call `with_cugraph_sql` **after** `install_on` (as
shown above) or use
`backend.install_on_with_cugraph_sql(builder, config)`: a cuGraph config
without its own admission authority automatically inherits the backend's, so
graph execution shares the backend admission owner. Installing cuGraph on the
builder *before* `install_on` is rejected at install time. Registering the
table functions directly on an already-built `SessionContext`
(`register_cugraph_udtfs`) bypasses backend admission and is not safe for
backend-managed processes.

## cuVS SQL functions

`install_on` installs the relation-aware cuVS planner and the common GPU
function metadata surface. Build with the `cuvs` feature to execute
`cuvs_*` calls. Unlike cuGraph, there is no server-style enable flag for cuVS:
the Cargo feature and the session memory policy determine availability.

`NexusGpuBackend` currently owns bounded QueryService admission, while cuVS has
no lower-level bounded peak-memory preflight. A backend-managed bounded session
therefore rejects cuVS execution with structured `unsupported_operator`; it
never falls back to CPU. For local single-query embedded work, install the
planner with an explicitly unbounded direct configuration:

```rust
use datafusion::execution::SessionStateBuilder;
use datafusion_nexus::{
    native_exec::NexusNativeExecutionConfig,
    planner::NexusNativeOptimizerConfig,
    session::NexusSessionStateBuilderExt,
};

let state = SessionStateBuilder::new()
    .with_default_features()
    .with_nexus_native(
        NexusNativeOptimizerConfig::default()
            .with_native_execution_config(NexusNativeExecutionConfig::unbounded()),
    )
    .try_with_cuvs_sql()?
    .build();
```

Use this mode only when the process and GPU are dedicated to the work. See
[Vector Inputs](../cuvs/vector-inputs.mdx) for the relation contract and
[cuVS Functions](../cuvs/operations/index.mdx) for operation lifecycles.

## Direct optimizer install

For local single-query experiments, you can still install the raw optimizer rule
directly:

```rust
use datafusion::execution::SessionStateBuilder;
use datafusion_nexus::{
    planner::NexusNativeOptimizerConfig,
    session::NexusSessionStateBuilderExt,
};

let state = SessionStateBuilder::new()
    .with_default_features()
    .with_nexus_native(NexusNativeOptimizerConfig::default())
    .build();
```

That direct path does not create a shared admission owner. If multiple
`SessionContext`s or concurrent queries use independent bounded configs on the
same GPU, each config has its own device budget. On such a session, graph SQL
also refuses native relational work inside a `cugraph_*` call (a structured
error at execute time) rather than stack a second full-budget
ledger. Use `NexusGpuBackend` whenever the embedding process can run more than
one GPU query at a time or mixes cuGraph with native execution.

The same metadata functions work in-process. Follow
[Discover & Validate GPU Functions](../guides/gpu-function-discovery.mdx)
before executing GPU work; the
[GPU Function Catalog API](../reference/gpu-function-catalog.mdx) defines
`gpu_list_functions()`, `gpu_describe_function(...)`, and
`gpu_validate_call(...)` for your `SessionContext`.
