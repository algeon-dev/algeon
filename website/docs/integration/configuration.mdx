# Configuration

Algeon has three configuration owners. Keep them separate:

| Surface              | Configure with                                  | Owns                                                                   |
|----------------------|-------------------------------------------------|------------------------------------------------------------------------|
| Flight SQL process   | `ServerConfig`, TOML, and environment variables | Listen address, admission, auth, workspace overlay, and retention      |
| Embedded GPU backend | `AlgeonGpuBackend::builder()`                   | Device ownership, capacity, queues, and execution mode                 |
| DataFusion session   | `SessionConfig`                                 | Standard DataFusion behavior (catalogs, batch size, target partitions) |

This page covers the Flight SQL process. For an embedded Rust service, use [DataFusion Session](./datafusion-session.mdx).

## How server configuration is resolved

`ServerConfig::from_env()` starts with built-in defaults, reads the TOML file
named by `ALGEON_SERVER_CONFIG_FILE`, and then applies environment overrides for
matching scalar admission, native, and observability fields.

The TOML file accepts only `[auth]`, `[admission]`, `[native]`,
`[observability]`, and `[models]`. Unknown fields fail startup. cuGraph and
workspace settings use the environment; standard DataFusion settings come from
its environment mapping or the embedded `SessionConfig` API.

## Minimal GPU server

Every selected CUDA ordinal needs exactly one TOML device profile, even when
all device-local values use their defaults:

```toml
# server.toml
[[admission.device_profiles]]
device_ordinal = 0
```

```bash
export ALGEON_SERVER_CONFIG_FILE="$PWD/server.toml"
export ALGEON_SERVER_GPU_DEVICES=0

flock /tmp/cudf-gpu.lock bash scripts/dev/run_server.sh
```

The profile above uses automatic device capacity, two active attempts, one
source-work slot, no resident GPU cache, and engine-derived installation
bounds. For a production deployment, set explicit limits only where the
deployment needs them.

## Admission

| Environment variable | Default | Purpose |
| --- | --- | --- |
| `ALGEON_SERVER_BIND` | `0.0.0.0:50051` | Flight SQL listen address |
| `ALGEON_SERVER_LOG` | `info` | Tracing filter |
| `ALGEON_SERVER_CONFIG_FILE` | unset | TOML overlay path |
| `ALGEON_SERVER_STATEMENT_TICKET_TTL_SECS` | `300` | How long an unconsumed Flight statement ticket may wait for `DoGet` |
| `ALGEON_SERVER_GPU_DEVICES` | `0` | Comma-separated CUDA ordinals |
| `ALGEON_SERVER_ADMISSION_MAX_QUEUED_ATTEMPTS` | `64` | Maximum queued admission waiters |
| `ALGEON_SERVER_ADMISSION_MAX_QUEUE_WAIT_MS` | `30000` | Maximum wait for a compatible device |

The two queue values can also be placed under `[admission]` as
`max_queued_attempts` and `max_queue_wait_ms`. Environment values win.
Admission is FIFO among capability-compatible waiters; there is no overtaking
or protected-waiter setting. The queue wait ends when a device grant is placed;
building the query's execution context after that is bounded by the query's own
deadline and cancellation, not by the queue wait.

After `device_ordinal`, a profile accepts `memory_limit_bytes`,
`backend_reserve_bytes`, `default_query_limit_bytes`, `max_active_attempts`,
`source_work_per_attempt`, `cache_cap_bytes`, and the optional telemetry flag
(`install_telemetry`). Configure `stream_pool_size`, `worker_count`, and
`lane_count` together or omit all three. `worker_count` is the number of GPU
execution workers on the device. One worker is reserved for context setup and
release cleanup, so a placed query builds its execution context and a finished
query returns its resources while every other worker runs queries; query
execution uses the remaining workers. The default is `max_active_attempts + 1`,
and an explicit `worker_count` must be at least that. An explicit `memory_limit_bytes`
requires an explicit `backend_reserve_bytes`: automatic capacity already bakes
in driver headroom, but an explicit limit does not, so the reserve must be
declared (`0` is a valid, deliberate choice).

Selected ordinals and profile ordinals must match exactly. A profile outside
`ALGEON_SERVER_GPU_DEVICES`, a missing profile, or a duplicate ordinal is an
error. `cache_cap_bytes = 0` (the default) installs no resident GPU cache.
`default_query_limit_bytes` is the immutable cap granted to a query unless an
embedding caller supplies an explicit cap. It must be positive and no larger
than the device's managed capacity; planner memory estimates do not resize it.

Capabilities and memory ownership are not file settings. The shipped server
binary declares `WholeDeviceExclusive` ownership for every selected ordinal;
custom embedders must make that declaration through the Rust API.

## Native execution

### Execution mode

The default is `native_preferred`. To keep ordinary SQL on DataFusion CPU and
use the GPU only for explicit cuGraph and cuVS UDTFs, add this to the server
TOML alongside its device profiles:

```toml
[native]
execution_mode = "functions_only"
```

Or override it through the environment:

```bash
export ALGEON_SERVER_EXECUTION_MODE=functions_only
```

Accepted values are `native_preferred`, `functions_only`, and `native_required`.
See [Choose an execution mode](./datafusion-session.mdx#choose-an-execution-mode)
for their behavior, composition boundaries, host staging limits, and embedded
Rust configuration. This is backend policy, not a SQL `SET` option. UDTF
features, registration, device profiles, and GPU admission are still required.

### Native settings

Native settings are accepted both under `[native]` and through the environment:

| TOML field | Environment variable | Default |
| --- | --- | --- |
| `execution_mode` | `ALGEON_SERVER_EXECUTION_MODE` | `native_preferred` |
| `max_source_chunk_bytes` | `ALGEON_SERVER_NATIVE_MAX_SOURCE_CHUNK_BYTES` | 64 MiB |
| `max_row_groups_per_chunk` | `ALGEON_SERVER_NATIVE_MAX_ROW_GROUPS_PER_CHUNK` | `1` |
| `max_retry_attempts` | `ALGEON_SERVER_NATIVE_MAX_RETRY_ATTEMPTS` | `3` |
| `max_source_reads_in_flight` | `ALGEON_SERVER_NATIVE_MAX_SOURCE_READS_IN_FLIGHT` | `2` |
| `source_chunk_planning_mode` | `ALGEON_SERVER_NATIVE_SOURCE_CHUNK_PLANNING_MODE` | `conservative` |
| `statistical_aggregate_execution_mode` | `ALGEON_SERVER_NATIVE_STATISTICAL_AGGREGATE_EXECUTION_MODE` | `gpu_native_tolerant` |
| `final_plan_requirement` | `ALGEON_SERVER_FINAL_PLAN_REQUIREMENT` | unset |

`source_chunk_planning_mode` also accepts `local_parquet_throughput`.

`statistical_aggregate_execution_mode` controls the `stddev` and `var`
aggregate family. The default, `gpu_native_tolerant`, keeps them on the GPU,
but its results are not guaranteed to match DataFusion exactly: floating-point
bits can differ, and precision degrades when values are large relative to
their spread. Set `datafusion_exact_host_welford` when results must match
DataFusion. That mode copies the aggregate input to host memory, and a query
whose group keys or other aggregates in the same `GROUP BY` it cannot evaluate
exactly is not rewritten to native execution.

The only final-plan requirement is `no_datafusion_cpu`. Used alone, it has the
same effect as `execution_mode = "native_required"`. If both fields are set,
they must agree: combining it with `native_preferred` or `functions_only`
fails startup.

Native settings carry no device-budget planning placeholder. Device capacity
is owned solely by the ordinal-keyed [`[[admission.device_profiles]]`](#admission)
entries. `max_source_chunk_bytes` and `max_row_groups_per_chunk` are
independent: each defaults to the engine default (64 MiB / `1`) when unset,
and setting one no longer requires the other.

## Authentication

Authentication is TOML-only and defaults to `disabled`. Use that default only
on a trusted local network. Static Basic credentials can be exchanged for
server-issued bearer tokens:

```toml
[auth.mode]
kind = "basic_bearer"
token_ttl_secs = 3600

[[auth.mode.users]]
username = "alice"
password_hash = "$argon2id$v=19$m=19456,t=2,p=1$..."
```

`token_ttl_secs` is required and must be greater than zero; non-expiring
bearer tokens are not supported. `password_hash` must be a valid Argon2 PHC
string; plaintext is rejected. Usernames must be unique.

## Runtime observation retention

The defaults retain bounded per-query records and sealed reports. Change them
only when the service's traffic and exporter behavior require a different
budget. A data statement's runtime observation belongs to its execution
attempt. A metadata statement, such as a catalog query, runs no native work:
its runtime artifact is the control frame alone, and its query stats come from
the server's own capture.

| TOML field under `[observability]` | Environment override | Default |
| --- | --- | --- |
| `per_query_max_records` | `ALGEON_SERVER_OBSERVABILITY_PER_QUERY_MAX_RECORDS` | `65536` |
| `per_query_max_bytes` | `ALGEON_SERVER_OBSERVABILITY_PER_QUERY_MAX_BYTES` | 8 MiB |
| `active_logical_capture_max_bytes` | `ALGEON_SERVER_OBSERVABILITY_ACTIVE_LOGICAL_CAPTURE_MAX_BYTES` | Admission requirement plus 1 GiB |
| `global_sealed_max_count` | `ALGEON_SERVER_OBSERVABILITY_GLOBAL_SEALED_MAX_COUNT` | `1024` |
| `global_sealed_max_bytes` | `ALGEON_SERVER_OBSERVABILITY_GLOBAL_SEALED_MAX_BYTES` | 1 GiB |
| `sealed_ttl_secs` | `ALGEON_SERVER_OBSERVABILITY_SEALED_TTL_SECS` | `3600` |
| `shutdown_grace_secs` | `ALGEON_SERVER_OBSERVABILITY_SHUTDOWN_GRACE_SECS` | `30` |

All values must be greater than zero.

Every live Flight SQL query reserves logical capture bytes from
`active_logical_capture_max_bytes` until it finishes: twice
`per_query_max_bytes`, plus `per_query_max_bytes`, plus its sealed artifact
(twice `per_query_max_bytes`, capped at `global_sealed_max_bytes`), which is
40 MiB with the defaults. A query also holds its reservation while it plans
and finalizes, outside its admission slot. The budget never refuses a query.
One that does not fit runs without capture: the server keeps none of its SQL
text, and its query stats, while it runs and after it ends, report
`unavailable_reason=active_capture_budget`.
Admission alone decides overload.

When the field is unset, the server sets it to the capture of every attempt
admission can hold at once (the sum of each device profile's
`max_active_attempts` and `admission.max_queued_attempts`) plus 1 GiB. Queries
reserve capture in the order they register, and statements that plan,
finalize, or never take an admission slot hold reservations too, so a query
within the admission bounds can still run without capture. The server logs
the budget and that admission requirement at startup.

The server registers at most 1024 live Flight SQL statements. This is a hard
cap on every live statement: one that is planning, ticketed but not yet read,
executing (CPU-only and metadata statements included), or finalizing counts
against it. Startup and `FlightSqlServerBuilder::build` fail with
`admission_exceeds_live_query_capacity` when the admission bounds alone hold
1024 attempts or more. Its `config_field` is
`ALGEON_SERVER_ADMISSION_MAX_QUEUED_ATTEMPTS`, or
`admission.device_profiles.max_active_attempts` when the device profiles fill
the cap by themselves.
Because statements outside admission share the cap, registration can refuse a
statement while admission still has room.

## GPU SQL UDTFs

cuGraph registration is controlled by these settings:

| Variable | Default | Purpose |
| --- | --- | --- |
| `ALGEON_SERVER_CUGRAPH_ENABLED` | `true` | Register the `cugraph_*` SQL frontend |
| `ALGEON_SERVER_CUGRAPH_CONSTRUCTION_POLICY` | `python_cugraph` | `python_cugraph` or `raw_libcugraph` |

The construction-policy override is rejected when
`ALGEON_SERVER_CUGRAPH_ENABLED` is false. A binary without the `cugraph` feature can still expose the frontend,
but execution returns a structured `required_feature_disabled` error.
Per-call named `construction_policy` and other graph values override these defaults; see
[Graph Inputs and Construction](../cugraph/graph-options.mdx).

cuVS has no enable variable. The server installs cuVS SQL on every session it
builds; the `cuvs` feature decides whether the UDTFs execute or return a
structured `required_feature_disabled` error. See
[cuVS execution](../cuvs/overview.mdx#execution).

## Models and forest inference

`cuml_forest_predict` reads its model file from a server-configured models
root. Without a `[models]` table, the UDTF is listed by
`gpu_list_functions()` but unavailable with `model_root_unconfigured`:

```toml
[models]
root = "/srv/models"
max_model_bytes = 268435456
```

| TOML field under `[models]` | Required | Default |
| --- | --- | --- |
| `root` | yes, to enable `cuml_forest_predict` | unset |
| `max_model_bytes` | no; requires `root` | 256 MiB |

`root` must exist and be a directory at startup; a missing or non-directory
path fails startup. The server opens that directory once at startup and
resolves every `model` beneath the opened directory, so renaming `root` or
replacing it (or a symlink among its ancestors) later does not redirect
lookups; restart the server to point at a new directory. Model lookup uses
`openat2(2)`, which requires Linux 5.6 or newer. `max_model_bytes` must be
positive when set. There is no environment override for either field.
Embedded sessions pass the same settings as `CumlModelStoreConfig` through
`try_with_cuml_sql_config`.

A `model` option passed to `cuml_forest_predict` is a path relative to
`root`; absolute paths and `..` components are rejected with
`model_path_rejected`. Relative symlinks that stay beneath `root` are
followed; an absolute symlink, or one whose target leaves `root`, is rejected
as `outside_root` without looking up the target. Only regular files are
accepted (FIFOs, directories, and other special files are rejected). A file larger than
`max_model_bytes` is rejected with `model_too_large`; a file nvForest cannot
parse, or a multi-target model, is rejected with `model_rejected`. A lookup
that keeps racing concurrent renames or mounts under `root` is rejected with
`model_path_rejected` and rejection `resolution_retry_exhausted`. The
statement reads and binds the model once at planning, and its SHA-256 digest
appears in `EXPLAIN` output as `model=sha256:<first 12 hex>`. Over Flight
SQL, a model file that changes on disk between `GetFlightInfo` and `DoGet`,
or between preparing and executing a prepared statement, fails the statement
with `model_changed`; the statement must be planned again.

Every file reachable beneath `root`, including hard links and bind mounts
placed there, is trusted as a model source, so `root` and its subdirectories
must not be writable by untrusted users. The model file is read and parsed
synchronously on each planning pass (`GetFlightInfo`, `DoGet`, and prepared
statement creation), so a large model adds its read and parse time to the
planning latency of every statement that names it.

## Removed Iceberg settings

The server has no Iceberg integration. Startup fails with an error that names
the variable and says it belonged to the removed integration when any of these
has a non-blank value:

- `ALGEON_ICEBERG_CATALOG_KIND`, `ALGEON_ICEBERG_CATALOG_NAME`,
  `ALGEON_ICEBERG_NAMESPACE`, `ALGEON_ICEBERG_TABLES`,
  `ALGEON_ICEBERG_WAREHOUSE`, and `ALGEON_ICEBERG_SCAN_PLANNING_TIMEOUT_SECS`
- `ALGEON_ICEBERG_GLUE_CATALOG_NAME`, `ALGEON_ICEBERG_GLUE_CATALOG_ID`,
  `ALGEON_ICEBERG_GLUE_URI`, `ALGEON_ICEBERG_REST_URI`,
  `ALGEON_ICEBERG_REST_PREFIX`, `ALGEON_ICEBERG_REST_TOKEN`, and
  `ALGEON_ICEBERG_REST_CATALOG_HANDLE`
- `ALGEON_ICEBERG_S3_ENDPOINT`, `ALGEON_ICEBERG_S3_REGION`,
  `ALGEON_ICEBERG_S3_PATH_STYLE`, and `ALGEON_ICEBERG_S3_CREDENTIAL_SOURCE`
- `ALGEON_LAKEHOUSE_CACHE_ROOT`, `ALGEON_LAKEHOUSE_CACHE_READ`,
  `ALGEON_LAKEHOUSE_CACHE_POLICY`, and `ALGEON_LAKEHOUSE_CACHE_MAX_BYTES`

Remove them from the deployment environment. The last group means a server
process cannot enable the persistent lakehouse byte cache for `s3://` Parquet
files. See [Iceberg support](./overview.mdx#iceberg-support) for the status of
Iceberg sources.

## Parquet source flags

Native scans read local and `s3://` Parquet files. Remote reads go through
KvikIO, which reads `AWS_DEFAULT_REGION`; the engine's own S3 metadata reads
use `AWS_REGION` first. Set both to the same region.

`KVIKIO_COMPAT_MODE=ON|OFF|AUTO` and `ALGEON_ICEBERG_FOOTER_PRUNING` are not
`ServerConfig` fields; set them in the process environment before startup.
`ALGEON_ICEBERG_FOOTER_PRUNING=true` enables Parquet-footer row-group pruning
for `s3://` scans (see
[Lakehouse and workspace boundary](../design/index.mdx#lakehouse-and-workspace-boundary)).
It accepts `true`, `false`, `1`, or `0` in any letter case, and an unset or
blank value means `false`. Any other value fails query planning. The variable
name predates the removal of the Iceberg integration.

## Workspace overlay

A workspace overlay keeps interactive DDL local and reads through to a backing
schema:

```bash
export ALGEON_SERVER_WORKSPACE_CATALOG=<workspace catalog>
export ALGEON_SERVER_WORKSPACE_SCHEMA=<workspace schema>
export ALGEON_SERVER_WORKSPACE_BACKING_CATALOG=<backing catalog>
export ALGEON_SERVER_WORKSPACE_BACKING_SCHEMA=<backing schema>
export ALGEON_SERVER_WORKSPACE_BACKING_ALIASES=<table>,<table>
```

The backing catalog and schema must be set together, and both must already be
registered in the server session, or session construction fails with a
configuration error. The standalone server registers no catalog beyond
DataFusion's default catalog. The workspace catalog and schema default to
`datafusion.public` and must differ from the backing pair. Omitting the aliases
exposes every backing table.

## DataFusion session configuration

The server builds DataFusion's `SessionConfig` with `SessionConfig::from_env()`.
Common keys include `DATAFUSION_EXECUTION_BATCH_SIZE`,
`DATAFUSION_EXECUTION_TARGET_PARTITIONS`,
`DATAFUSION_CATALOG_DEFAULT_CATALOG`, and
`DATAFUSION_CATALOG_DEFAULT_SCHEMA`.

Native execution policy is owned solely by the server configuration (`[native]` TOML options and `ALGEON_SERVER_NATIVE_*` environment variables) or the embedded `AlgeonGpuBackendBuilder`.
Algeon registers no session configuration extensions; DataFusion sessions carry standard DataFusion configuration only.
SQL statements attempting `SET algeon_datafusion.*` fail with an unrecognized configuration key error.
