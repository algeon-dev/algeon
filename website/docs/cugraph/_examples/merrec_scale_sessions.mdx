The events table has a `session_id` column, and grouping by it looks like
the obvious way to build sessions. A graph checks that assumption before
any session analysis depends on it. Every
October user and every session ID becomes a vertex, with an edge from a
user to each session ID in their events. If a session ID belonged to one
user, every connected component would contain exactly one user.

Graph vertices can be strings, so a user vertex is `user:` followed by the
user ID and a session vertex is the session ID itself. The two kinds cannot
collide. The query groups the components by how many users they contain.

The query took **{capture.median_elapsed_s_after_first.toFixed(2)} s** over
Flight SQL. An equivalent CPU pipeline combining 32-thread DuckDB with scipy's
connected components took **12.3 s** on the same machine (9.3 s in string
deduplication and renumbering, 3.0 s in WCC) and produced identical components.

One component links {n(capture.records.find(row => row.largest > 1000).users)} of
October's 2,986,296 users through shared session IDs. Only
{n(capture.records.find(row => row.largest === 1).users)} users have session
IDs that nobody else uses. Across the six months, 15,138,756 of the
25,864,474 distinct session IDs appear for more than one user, and one ID
appears for 54 users. Session analysis on this dataset has to group by
`(user_id, session_id)`. The query reveals repeated session IDs across multiple users
in the source records.

The same query, with the column substituted, audits any other identifier
such as a device, cart or order ID. A component with more than one owner is
the case to investigate.
