# cuGraph SQL API

Algeon exposes NVIDIA RAPIDS **cuGraph** algorithms as GPU UDTFs
(user-defined table functions) over DataFusion SQL sessions. The session can
run in a Rust process or be served through Flight SQL. Each `cugraph_*` UDTF
reads an edge relation, builds a GPU graph, runs an algorithm, and returns rows
you can compose with ordinary SQL.

This section helps you choose a graph UDTF, provide its edge relation, and
understand its execution and reuse boundaries.

## Graph input and call shape

Every cuGraph call uses named arguments. The required `edges` argument is a
parenthesized relation subquery whose projection supplies canonical `src` and
`dst` columns. Optional graph and algorithm values use the same named syntax:

```sql
SELECT *
FROM cugraph_pagerank(
  edges => (SELECT src, dst, weight FROM citation_edges),
  alpha => 0.9,
  directed => true
);
```

Algorithms that need additional relations name them explicitly, for example
`personalization => (SELECT vertex, value FROM ppr_seeds)` for personalized
PageRank or `vertex_pairs => (SELECT first, second FROM candidate_pairs)` for
similarity UDTFs. BFS source selectors and SSSP's source vertex are named
value arguments as well. Each UDTF page gives the complete signature and
the canonical columns required for every relation role.

Relation subqueries can read tables, views, CTEs, joins, and filters. Register
a derived relation as a temporary view when it must also be checked through
`gpu_validate_call`, because the metadata envelope resolves registered names
and does not contain SQL text. See [Integrating Algeon](../integration/overview.mdx)
for source and session setup, and [Graph Inputs and Construction](./graph-options.mdx)
for vertex-ID contracts, directedness, vertex renumbering, and edge
normalization.

The [GPU table functions design](../design/gpu-table-functions.mdx#from-cudf-columns-to-a-cugraph-result)
traces cuDF edge ownership, cuGraph completion and the return to native SQL
operators. It distinguishes device copies from host materialization.

## Result column names

Result columns follow one naming convention across UDTFs. The edge input
columns (`src`, `dst`, `weight`, `edge_id`) are separate and keep their names.

| Result | Columns |
| --- | --- |
| Vertex identity | `vertex` |
| One score per vertex | `value` |
| Edge | `src`, `dst`, plus `value` for an edge score |
| Community assignment | `community` |
| Connectivity label | `component` |
| Vertex pair similarity | `first`, `second`, `similarity` |

Each UDTF page lists its exact result schema, including algorithm-specific
columns such as `hub_score` and `authority_score` for HITS.

## Reuse in bounded servers

A bounded Flight SQL server can retain constructed graphs for repeat calls with
a strongly identified, eligible input. The current reusable path covers BFS
without `include_edges`, PageRank, Jaccard, Sorensen, Overlap, and Cosine;
other calls bypass the cache. Configure and observe it through
[Configuration](../integration/configuration.mdx).
