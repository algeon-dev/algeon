# Graph Inputs and Construction

Every `cugraph_*` UDTF builds a GPU graph from an edge relation. Before
choosing algorithm-specific options, establish two parts of the graph input
contract:

- the vertex-ID domain carried by the source and destination columns;
- the construction semantics applied to the edge rows.

The concrete UDTF descriptor remains authoritative when an algorithm
narrows either part of this shared contract.

## Vertex codebook

A call whose vertex type the native algorithm cannot index maps each distinct
vertex to a dense id of the native vertex id type in the table above, runs the
algorithm on those ids and decodes the returned ids to the input vertex type,
so the SQL needs no mapping table. String vertices are mapped for every
algorithm. `cugraph_spectral_modularity_maximization` and
`cugraph_minimum_spanning_tree` run on Int32 ids, so they also map Int64
vertices, and their distinct vertex count must fit in Int32.

The mapping keeps the edge relation resident with both endpoint columns,
builds the distinct vertex set from both endpoints and joins the edge relation
to it once per endpoint. Peak device memory for a string-vertex call grows with
the string bytes of the edge relation and is several times the peak of the
same graph with Int64 vertex ids. When such a call exceeds the query memory
grant, assign Int64 surrogate ids in the edge subquery, for example by joining
the edges to a vertex table, and join the algorithm output back to the strings.

## Vertex id width

libcugraph stores one vertex id for every adjacency entry of the graph it
builds, in the type of the edge columns it receives. Before construction,
Algeon reads the minimum and maximum of the Int64 endpoint columns. When the
graph qualifies, it builds from Int32 copies of those columns. A call
qualifies when:

- every endpoint id, edge id, vertex id in a side input (source vertices,
  personalization vertices, vertex pairs, BFS predicate relations, seeds,
  ForceAtlas2 vertices) and literal vertex id lies in
  `[-2147483648, 2147483646]`;
- the edge relation has fewer than 2,147,483,647 rows after normalization;
- the number of distinct endpoint values can be at most 2,147,483,647.

A call that does not qualify keeps Int64 ids. A side-input id outside the
Int32 range therefore names a vertex that is not in the graph, with the same
outcome as on an Int64 graph. Result columns keep the declared vertex type,
and a BFS distance of a vertex the traversal does not reach stays the Int64
maximum. String and codebook-mapped calls apply the same rule to their dense
ids. For the functions whose results repeat between runs
([Reproducibility](../design/gpu-table-functions.mdx#reproducibility)), the
rows equal those of the same graph built with Int64 ids.

## Construction options

Every `cugraph_*` UDTF accepts these shared named value arguments alongside
any algorithm-specific values. They control how the GPU graph is built from the
edge relation.

| Option | Type | Default | Allowed values | Description |
| --- | --- | --- | --- | --- |
| `directed` | `Boolean` | `true` base default; some algorithms default to `false` | `true`, `false` | Whether graph construction treats edges as directed. |
| `renumber` | `Boolean` | `true` | `true`, `false` | Whether construction may renumber external vertex ids internally. |
| `construction_policy` | `Utf8` | `python_cugraph` | `python_cugraph`, `raw_libcugraph` | Edge-list construction semantics used before calling libcugraph. |

Per-algorithm option defaults can differ. `directed` defaults to `false` for
weakly connected components, triangle count, core number, k-core, minimum
spanning tree, spectral modularity maximization, and ForceAtlas2. The default
shown on each UDTF's page and from `gpu_validate_call` is authoritative
for that UDTF.

## Construction policy

`construction_policy` is a graph-ingress choice, not an algorithm choice. It
decides whether Algeon should first make the SQL edge relation match
Python cuGraph edge-list construction semantics, or pass the relation directly
to the lower-level libcugraph construction path.

Use `python_cugraph` unless you have a specific reason to bypass Python-style
edge normalization.

| Policy | Best use | What happens |
| --- | --- | --- |
| `python_cugraph` | Default for application SQL, notebooks, Python cuGraph parity checks, and edge tables that may contain duplicate or one-way undirected edges. | Requests Python `cugraph.Graph.from_cudf_edgelist(...)`-compatible construction. Algeon inserts an `EdgeNormalize` step when the edge source is not already proven canonical. |
| `raw_libcugraph` | Pre-normalized edge tables, lower-level libcugraph parity checks, and performance-sensitive paths where duplicate/reverse-edge semantics are intentionally handled upstream. | Skips Python-style `EdgeNormalize` and sends the edge list to the libcugraph-compatible graph builder. Null edge rows are still sanitized because libcugraph has no null-edge semantics. |

For SQL calls, both policies still use simple graph properties selected by
`directed`. There is no SQL multigraph option.

## What `python_cugraph` normalizes

When normalization is required, Algeon rewrites the edge list before graph
construction:

- `directed=true`: duplicate directed `(src, dst)` pairs are collapsed.
- `directed=false`: reverse `(dst, src)` rows are added, then duplicate directed
  pairs are collapsed.
- weighted duplicate conflicts are shape-specific: directed weighted graphs keep
  the last row in stable input order for each `(src, dst)` pair; undirected
  weighted graphs keep the minimum weight after reverse-edge expansion.

## Edge normalization and null handling

The optimizer may skip the physical `EdgeNormalize` operator even when the
selected policy is `python_cugraph`, but only when it can prove the input edge
source is already canonical for the requested `directed` and edge-column shape.

The planner proves that each `(src, dst)` pair appears once when the edge
relation groups on `src` and `dst` (`SELECT DISTINCT src, dst` or
`GROUP BY src, dst`), or reads one complete Parquet file whose footer carries
the `algeon.graph.simple_directed_edge_topology` certificate. With that proof
an unweighted `directed => true` call is canonical and `EdgeNormalize` is
skipped. A weighted `directed => true` call keeps the step, which then has
nothing to deduplicate.

A `directed => false` call still needs the reversed edges, so `EdgeNormalize`
stays in the plan and receives the proof. At run time it reads the minimum and
maximum of `src` and `dst`. When the two ranges do not overlap, as in a
user-to-item graph whose user ids are offset past the item ids, a reversed
edge cannot repeat an input edge, and the step appends the reversed edges
without deduplicating. Overlapping ranges, or a relation without the proof,
take the full deduplication.

With either construction policy, source and destination nulls are not valid
graph edges and are dropped before libcugraph receives the edge list. Null
weights or edge ids only drop rows when the planned algorithm consumes
that column.

## How to set it

Leave the option unset to use the default `python_cugraph` policy:

```sql
SELECT *
FROM cugraph_pagerank(edges => (SELECT src, dst FROM edges));
```

Override one call when the edge relation is already prepared for raw
libcugraph-style construction:

```sql
SELECT *
FROM cugraph_pagerank(
  edges => (SELECT src, dst, weight FROM canonical_edges),
  construction_policy => 'raw_libcugraph'
);
```

On the standalone Flight SQL server, set a process default with
`ALGEON_SERVER_CUGRAPH_CONSTRUCTION_POLICY`. A per-call named value still wins:

```bash
ALGEON_SERVER_CUGRAPH_CONSTRUCTION_POLICY=raw_libcugraph target/release/algeon_server
```

## Verify the planned path

Use `EXPLAIN` when the distinction matters:

```sql
EXPLAIN
SELECT *
FROM cugraph_louvain(
  edges => (SELECT src, dst, weight FROM edges),
  directed => false,
  construction_policy => 'python_cugraph'
);
```

Look for these fields in the physical plan:

- `construction_policy=python_cugraph` means the SQL call requested
  Python-compatible construction semantics.
- `edge_normalize_inserted=true` means Algeon will run a physical edge
  normalization step.
- `construction_policy=python_cugraph` with `edge_normalize_inserted=false`
  means the optimizer proved the input is already canonical for the requested
  Python-compatible semantics.
- `distinct_edge_pairs=true` means the planner proved that each `(src, dst)`
  pair appears once.

## Reuse algorithm results

A view stores a query definition. Each later query that reads it executes the
algorithm again.
Community partitions and layout coordinates can change between executions.
The [reproducibility section](../design/gpu-table-functions.mdx#reproducibility)
lists which functions repeat. Use `CREATE OR REPLACE TABLE ... AS` when later
queries need results from one execution, as in the
[SCC example](./udtfs/connectivity/cugraph_strongly_connected_components.mdx#examples).

CTAS executes the query and collects its results into a DataFusion `MemTable`
in host RAM. A later GPU query uploads the required data again. These result
tables last until the server stops and leave the source Parquet files unchanged.
Include materialization and result collection in end-to-end timing.
