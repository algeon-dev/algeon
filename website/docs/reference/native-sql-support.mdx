# Native SQL Support

Algeon selects supported whole relational DataFusion physical-plan candidates
for cuDF execution. Support is capability-first: every operator, expression,
type, and source in the exact physical candidate must have a native kernel
with matching semantics. Memory is not a support criterion; an admitted query
runs inside its granted cap and fails with a typed allocation error if it
exceeds it. This page is a practical map, not a substitute for validating a
production query with
[`algeon_explain_coverage`](../integration/gpu-coverage-validation.mdx).

## Relational plan shapes

| Area | Native forms |
| --- | --- |
| Sources | Local and S3 object-store Parquet; projected columns, row-group selection, partition columns, reader predicates, and scan limits when their contracts are supported. |
| Row operations | Filters, projections, stable or unstable sorts, `LIMIT`/`OFFSET`, and schema-compatible `UNION ALL`. A distinct `UNION` and `SELECT DISTINCT` are grouped aggregates, listed under Aggregation. |
| Aggregation | Global and grouped aggregation, admitted grouping sets, aggregate filters, and partial/final state when the state is explicitly modeled. |
| Windows | `rank`, `row_number`, `lag`, `lead`, whole-partition aggregate windows, and cumulative `sum`/`min`/`max` over `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`. `rank`, `lag`, and `lead` require `ORDER BY`; `row_number` does not. An aggregate window with an empty `OVER ()` aggregates the whole input as one partition, beside other windows and under filters. |
| Joins | Equi joins and admitted residual/keyless forms for inner, outer, semi, anti, mark, and cross joins. Build side, output projection, key types, and residual expressions can narrow an otherwise supported join kind. |
| Graph | cuGraph UDTFs are a separate GPU execution domain. See the [cuGraph SQL API](../cugraph/overview.mdx) for the UDTF-level contract. |

When a relational candidate is not supported, or an enabled cost rule does not
select it, the executable DataFusion baseline remains in place. Runtime errors
after native execution starts are terminal and do not replay on CPU.

## Expressions and scalar functions

Native filter and projection expressions include columns and literals,
arithmetic and comparisons, boolean logic, null tests, supported casts,
case-sensitive `LIKE`, literal `IN` lists, `CASE`, and string-to-integer
`TRY_CAST`.

Integer `+`, `-`, `*`, and unary minus wrap on overflow, as DataFusion does
for column values. Integer `/` and `%` evaluate only the rows where both
operands are valid. A zero divisor in such a row fails the query, as does
`/` on the minimum signed value divided by `-1`; `x % -1` is `0`. Rows with a
null operand stay null and never fail. Floating-point `%` follows IEEE `fmod`:
the result takes the sign of the dividend, and a zero divisor or an infinite
dividend gives `NaN`. `%` on decimals is not native. Integer `/` and any `%` are
not evaluated inside reader predicates or join residual conditions, nor is
timestamp `+` or `-`: a reader predicate with them stays a filter, and a join
residual with them keeps the join on DataFusion.

Decimal `/` evaluates the same valid rows and fails on a zero divisor. DataFusion
computes `dividend * 10^k / divisor` on the raw values in checked `i128`
arithmetic, where `10^k` gives the quotient the result scale, which is the
dividend scale plus 4 capped at 38. The query therefore also fails when a valid
dividend times `10^k` leaves the `i128` range, and when that product is the
minimum `i128` value and the raw divisor is `-1`. Native evaluation fails on
the same rows. A
quotient that needs more digits than the result precision is not an error in
DataFusion or in native evaluation. A join residual with a decimal `/` keeps the
join on DataFusion.

Explicit `CAST` runs natively between integer types, from `Float32`,
`Float64`, and `Decimal128(p, 0)` to integer types, and from integers to
`Utf8`, `LargeUtf8`, and `Utf8View`. Like DataFusion `CAST`, a cast to an
integer type fails the query when a valid value is outside the target range.
Floating-point and decimal inputs truncate toward zero before the comparison,
and a `NaN` or infinite float fails. Integer-to-string casts produce plain
decimal text with a leading `-` for negative values, so
`CAST(row_number() OVER (ORDER BY id) AS BIGINT)` and `CAST(user_id AS VARCHAR)`
are native. Casting a float or boolean to a string is not.

A timestamp without a time zone, or a duration, casts to `BIGINT`. As in Arrow,
the result is the stored count in the type's own unit, with no rescaling:
`CAST(event_time AS BIGINT)` over a `TIMESTAMP(3)` column gives milliseconds
since the Unix epoch, and a `Duration(Millisecond)` gives its millisecond count.
Nulls stay null, and the cast cannot fail. A cast to any other numeric type, and
any cast from a timezone-aware timestamp, stays on DataFusion.

A cast between two units of a timestamp without a time zone, or of a duration,
follows Arrow. A cast to a finer unit multiplies the stored count and fails the
query when the product of a valid row leaves `Int64`. For
`CAST(t AS TIMESTAMP(9))` over a `TIMESTAMP(0)` column that is a count above
9223372036 or below -9223372036, about 292 years from the epoch. A `DATE` cast to a timestamp fails
the same way at microsecond and nanosecond resolution, and at nanosecond
resolution from 106,752 days away from the epoch. A cast to a coarser unit
divides and truncates toward zero: `-1500` milliseconds becomes `-1` second, and
`-1` nanosecond becomes `0` seconds. A cast from a timestamp to `DATE` takes the
calendar date, which floors, so `-1` nanosecond is the day before the epoch. An
integer casts to a timestamp as the count of the target unit since the epoch,
without rescaling. Nulls stay null.

Subtracting two timezone-free timestamps of one unit gives a `Duration` of that
unit. Combined with the cast, `CAST(next_view - event_time AS BIGINT)` is the
number of milliseconds between two millisecond-resolution events, with
`next_view` taken from `LEAD` or `LAG`. DataFusion casts the coarser operand of
two different units to the finer unit first, which is the checked cast described
above, and arithmetic between two durations is not native.

A timezone-free timestamp plus or minus a duration of the same unit, and a
duration plus such a timestamp, give a timestamp of that unit. DataFusion casts
a duration of another unit to the timestamp's unit before it adds, with the
checked cast described above, so the addition itself always sees one unit. A
date plus or minus a duration is not native. It is not valid in DataFusion
either, because Arrow defines no such operation: `date_col + duration_col`
fails planning with `Cannot coerce arithmetic expression Date32 + Duration(ms)
to valid types`, and `Date64` fails the same way. The difference of two dates is
an integer day count in DataFusion and is not native.

Unlike integer `+` and `-`, timestamp arithmetic does not wrap. Arrow checks
a timestamp plus or minus a duration, and the difference of two timestamps,
even for the wrapping SQL operators, so a result outside `Int64` fails the
query. Native evaluation fails on the same rows: a valid row of both operands
whose result does not fit, which takes operands more than 292 years apart at
nanosecond resolution. A null operand never fails. A timestamp plus or minus an
`INTERVAL` is a separate calendar computation and is not checked this way.

A cast into `Decimal128(p, s)` from an integer, a float, or another
`Decimal128` rounds half away from zero where it drops digits. It fails the
query when a valid value does not fit precision `p` after rescaling, and when a
float is `NaN` or infinite. A float is rounded as `round(10^s * value)` in
`Float64`, the way DataFusion does it.

DataFusion evaluates a `CASE` result only on the rows where its condition is
true, `ELSE` only on the rows where no condition is true, and every `WHEN`
after the first only on the rows no earlier `WHEN` selected. In
`CASE base WHEN value`, it evaluates `value` only where `base` is not null. A
null condition counts as not true. The native evaluator visits every row, so
lowering sets the divisor of an integer `/` or `%`, the right operand of a
timestamp `+` or `-`, and the input of a cast that range-checks, to null on the
rows DataFusion does not evaluate. A null operand never fails.
`CASE WHEN n <> 0 THEN total / n END` never divides by zero, while
`CASE WHEN n >= 0 THEN total / n END` fails the query on a row with `n = 0`, as
on DataFusion. A nested `CASE` applies the restrictions of every enclosing
branch. A literal integer divisor other than `0` and `-1` and a cast whose
target holds every value of the source type cannot fail and are evaluated as
they are. A decimal `/` is always restricted, because scaling its dividend can
overflow whatever the divisor is. Timestamp `+` and `-` are always restricted,
because any pair of operands can overflow. Each `WHEN` condition that divides,
casts, or does timestamp arithmetic doubles the restrictions of the branches
after it, so a `CASE` with a long chain of such conditions (about eight) stays
on DataFusion.

DataFusion skips the right operand of `AND` on the rows where the left operand
is false, and the right operand of `OR` on the rows where it is true, only in
some batches. It skips every such row when all left values decide the result,
and the deciding rows when the left values contain no null and at most a fifth
of them are undecided. Any other batch, including every batch whose left values
contain a null, evaluates the right operand on every row. Native evaluation
never runs a fallible operation of the right operand on a row the left operand
decides, with the restrictions described for `CASE`: for `l AND r` the
operation runs where `l` is true or null, and for `l OR r` where `l` is false or
null. `WHERE n <> 0 AND total / n > 1` never divides by zero, while
`WHERE n >= 0 AND total / n > 1` fails the query on a row with `n = 0`. A decided
row takes its value from the left operand alone, so results do not change.
Native evaluation is more permissive than DataFusion in one case: where
DataFusion evaluates the right operand on a decided row that fails, it fails the
query and native evaluation returns the result. Native evaluation never fails
where DataFusion succeeds. An `AND` or `OR` term that divides, casts, or does
timestamp arithmetic doubles the restrictions of the terms after it, so a chain
of about eight such terms stays on DataFusion.

The supported DataFusion scalar-function names are:

| Family | Functions and important limits |
| --- | --- |
| Strings | `substring`/`substr`, `lower`, `upper`, `trim`/`btrim`, `ltrim`, `rtrim`, `contains`, `starts_with`, `ends_with`, `character_length`/`length`, `regexp_replace`, and `concat`. A substring start and optional length must be literal integers with start >= 1 and length >= 0. Pattern, trim, and replacement arguments that define the other operations must be literals. |
| Numeric | `abs`, `sqrt`, `ln`, `exp`, `floor`, `ceil`, and `round`; `round` accepts an optional literal integer scale. `floor` and `ceil` take `Float32` or `Float64` (DataFusion widens an integer argument to `Float64`) and pass `NaN` and infinities through; decimal arguments are not native. `ln` and `exp` follow IEEE results (`ln(0)` is `-inf`, a negative `ln` input is `NaN`) and can differ from DataFusion CPU in the last bits of finite results. |
| Nulls | `nullif` for compatible native types. |
| Temporal | `date_part`/`extract` for admitted date/timestamp fields, `date_trunc` for day through microsecond units on timezone-free timestamps, and `to_timestamp_seconds` for supported integer inputs. `date_part('epoch', ...)` is not native. DataFusion builds the epoch of a duration from 32-bit second and nanosecond fields, so it drops the fractional seconds of a duration longer than about 2.1 seconds, and native evaluation does not reproduce that. Cast to `BIGINT` and divide instead, for example `CAST(d AS BIGINT) / 1000.0` for milliseconds. |

Exact dtype rules still apply and are owned by
[Data Type Support](./data-type-support.md). In short: timezone-aware
timestamps, the [basic-list carry matrix](./data-type-support.md#basic-list-carry-matrix),
the numeric [`FixedSizeList<T, D>` matrix](./data-type-support.md#numeric-fixed-size-list-carry-matrix),
and the [narrow-decimal carry matrix](./data-type-support.md#narrow-decimal-carry-matrix)
are carry types: they can be selected and returned unchanged but are not valid
expression values, keys, sort or partition values, or aggregate and window
inputs. Each matrix on that page states what the output schema preserves.

## Aggregates

Native aggregate functions are `sum`, `min`, `max`, `count`, `avg`, `median`,
`stddev`/`stddev_samp`, `stddev_pop`,
`var`/`variance`/`var_samp`/`var_sample`, and
`var_pop`/`var_population`. `COUNT(DISTINCT expression)` is supported; other
distinct aggregates are not. Ordered aggregate arguments are not supported.

Aggregate mode matters. AVG uses explicit sum/count state for partial/final
execution and divides as DataFusion does: a `Decimal128` average truncates
toward zero at its output scale. AVG over a `Decimal128` argument with
precision above 25 is not native, because DataFusion sums it as `Decimal256`.
Median is single-stage, and plans that mix median with floating statistical
aggregates are rejected.

`SELECT DISTINCT` and a distinct `UNION` are grouped aggregates over every
output column with no aggregate function, so they follow the same partial/final
rules. DataFusion's final stage reads the partial stage through a repartition,
a coalesce, or a merge of sorted partitions without a fetch. The merge appears
when a Parquet source declares its sort order and the partial stage has several
partitions, for example below a `UNION`, because DataFusion then streams the
final stage over sorted groups. All three lower to one native aggregate. A
final stage that reads any other operator is rejected, and the rejection names
that operator.

An aggregate containing `COUNT(DISTINCT expression)` reads its whole input
before grouping, and that input must fit the query's device-memory grant. The
native optimizer splits such an aggregate when every distinct count reads the
same expression without `FILTER`, the remaining aggregates are `sum`, `min`,
`max`, `count` or `avg`, and there are no grouping sets. The first grouping
uses the keys plus that expression and holds one row for each distinct pair;
the second uses the keys alone. Both merge state across input chunks, and an
`avg` keeps its sum and count until the second grouping finishes. A `median`
or statistical aggregate beside the distinct count keeps the whole-input form.

Floating statistical aggregates (`stddev` and `var` variants) run under the
GPU-tolerant policy by default, so their results can differ from DataFusion.
The exact-host policy matches DataFusion but supports fewer group-key and
aggregate types. See
`statistical_aggregate_execution_mode` in
[configuration](../integration/configuration.mdx).

## Source boundaries

Parquet is the native data-file format, read from local paths or `s3://`
object stores. Schema mapping and remote read capability are validated before
execution, and a scan that fails either check keeps the executable DataFusion
baseline. Iceberg tables are not a supported source; see
[Iceberg support](../integration/overview.mdx#iceberg-support).

For ad-hoc SQL, validate against the same catalog and server configuration that
will execute the query:

```sql
SELECT row_kind,
       gpu_path,
       candidate_shape,
       reason_code,
       remedy_code,
       remedy,
       coverage_json
FROM algeon_explain_coverage('
  SELECT l_returnflag, sum(l_quantity)
  FROM lineitem
  WHERE l_shipdate >= DATE ''1996-01-01''
  GROUP BY l_returnflag
  ORDER BY l_returnflag
');
```

The `summary` row reports `gpu_path`: `native`, `partial_native`, `cpu`, or
`rejected`. Candidate rows make the stable reason and remedy first-class
columns; `coverage_json` on the summary retains projected candidate
source-capability and cost evidence, plus runtime and configuration evidence.
Flight SQL users can write `EXPLAIN GPU <query>` for
the identical schema without escaping the query into a SQL literal. Read
`runtime_caveats` too: admission, data-dependent memory, and device-side graph
validation are execution-time contracts.
