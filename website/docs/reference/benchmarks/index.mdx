# Benchmarks

## GPU algorithms

The GPU algorithms behind `cugraph_*`, `cuvs_*` and `cuml_*` UDTFs run NVIDIA's native
libraries inside DataFusion physical plans alongside relational operators. NVIDIA
publishes upstream kernel benchmarks for [cuGraph](https://docs.nvidia.com/cugraph/latest/nx_cugraph/benchmarks/#benchmarks),
[cuVS](https://developer.nvidia.com/topics/ai/generative-ai/cuvs#section-performance),
and [cuML](https://docs.nvidia.com/cuml/latest/cuml-accel/benchmarks/#inference-and-transforms).

### MerRec queries against CPU pipelines

Each query reads the full six-month [MerRec dataset](../../guides/datasets/merrec.mdx),
1,268,092,738 events and 82,614,392 items on local NVMe, with the files in the
page cache. Each CPU pipeline runs the relational steps in DuckDB 1.5.6 on 32
threads and the algorithm in the named library. Both sides ran on one host: an
Intel Xeon Platinum 8559C with 32 vCPUs, 256 GiB RAM and an NVIDIA RTX PRO 6000
with 96 GB.

<details>
<summary>Where the time goes</summary>

- **Barbie tie-ins** builds two undirected like graphs from 23 million distinct
  user-brand pairs and runs personalized and global PageRank on each. The CPU
  pipeline spends 2.3 s in the DuckDB join, 13.0 s renumbering vertices and
  building the igraph graphs, and 7.7 s in the four PageRank calls. NetworkX 3.7
  needs 158 s once its tolerance matches cuGraph's absolute L1 tolerance
  (`tol = 1e-5 / N`). Its default `tol=1e-6` is a mean per-vertex error and
  stops after one or two iterations on 2.1 million vertices.
- **Session audit** finds weakly connected components over 39.8 million
  user-session edges. DuckDB deduplication and renumbering take 9.3 s, then
  scipy `connected_components` takes 3.0 s.
- **Audience funnel** combines graph affinity, taste lookalikes and purchase
  propensity in one plan. The CPU pipeline hands intermediate tables through
  igraph, FAISS and XGBoost in host memory; graph construction and personalized
  PageRank alone take 14 s. Shoppers tied at the 20th-neighbour distance fall on
  either side of the cutoff, so the lookalike count varies by up to four of
  about 19,100.
- **Propensity model** aggregates per-shopper features from the events before
  September and scores 2.0 million shoppers with an existing XGBoost model. The
  feature aggregation takes 14.7 s in DuckDB and most of the 6.6 s on the GPU;
  forest inference takes 1.1 s in XGBoost and 0.03 s in cuML. Three shoppers
  with tied scores sit at the shortlist cutoff, so one buyer count reads
  16,087 on the GPU and 16,090 on the CPU.
- **Brand twins** compares the fan sets of the 2,000 largest brands. The CPU
  pipeline computes Jaccard as a DuckDB self-join: 2.9 s to collect fans and
  3.4 s for the join.
- **Pokemon lookalikes** builds a 64-dimensional taste vector for each of 2.1
  million shoppers in SQL, then searches 20 neighbours of each seed buyer.
  Building the vectors takes 19.5 s in DuckDB and most of the 13.8 s on the
  GPU. The FAISS search takes 6.4 s and the cuVS search 0.03 s.
- **Shopping worlds** groups the 5,000 largest brands into worlds with Leiden
  over a Jaccard similarity graph. DuckDB spends 8.3 s on the fan sets and Jaccard and igraph
  0.5 s on Leiden. The two Leiden implementations return different
  partitions, so the result lists cannot be compared row by row.
- **World bridges** scores 12.5 million brand pairs with Jaccard similarity,
  splits the similarity graph into worlds with Leiden and ranks bridge brands
  by exact betweenness. The DuckDB self-join for Jaccard takes 6.2 s and
  networkit's parallel betweenness 1.7 s. cuGraph and igraph partition the
  graph differently, so the comparison covers the betweenness ranking and
  neighbour counts.

</details>

## Relational path

The TPC-H and TPC-DS suites at scale factor 100, CPU path against GPU path,
one warm-up and one measured iteration per query, on an AWS EC2 **g7e.8xlarge**.
These runs are derived from the TPC-H and TPC-DS benchmarks. They are not
audited TPC results and are not comparable to published TPC results. TPC-H
and TPC-DS are trademarks of the Transaction Processing Performance Council.
The query text is the DuckDB rendering of the TPC specifications (MIT).

- CPU: Intel Xeon Platinum 8559C, 32 vCPU.
- Memory: 256 GiB.
- GPU: NVIDIA RTX PRO 6000 Blackwell Server Edition, 96 GB.
- Storage: local NVMe Parquet files. GPU reads use KvikIO compatibility mode
  with Algeon's default 64 I/O threads, without GPUDirect Storage. CPU reads
  use DataFusion's Arrow Parquet reader.
- DataFusion version `55.1`.

<details>
<summary>TPC-DS reproduction and parity verification</summary>

Both paths use release builds with `target-cpu=x86-64-v3` and the same 24
Parquet files, totalling 41,372,641,702 bytes and 959,037,905 rows. No caches
were flushed. Each query's warm-up precedes its measured execution. `wall_ms`
measures execution through result collection, including reads and GPU result
transfer. Successful-query SQL and physical planning time are excluded.

GPU runs use the `sf100_gpu_throughput` profile with
`local_parquet_throughput` source planning, an explicit 32 GiB
`max_source_chunk_bytes` target and at most 1,024 row groups per chunk.
The byte target groups source data; the query's separate
[memory grant](../../design/admission.mdx#device-profiles-and-grants) limits
device allocations. This benchmark profile sets its row-group cap directly.
The server's [default chunk policy](../../integration/configuration.mdx#native-settings)
derives its byte target from the admitted grant. Statistical aggregates use
[`gpu_native_tolerant`](../../integration/configuration.mdx#native-settings).

The recorded source is commit
<code>{tpcdsSf100Benchmark.environment.sourceRevision.slice(0, 12)}</code>.
The TPC-DS environment variables select the CPU partition and batch settings:

```bash
source env.sh
export ALGEON_TPCDS_CPU_TARGET_PARTITIONS=32
export ALGEON_TPCDS_CPU_BATCH_SIZE=32768
export ALGEON_TPCDS_NATIVE_PROFILE=sf100_gpu_throughput
export ALGEON_TPCDS_NATIVE_STATISTICAL_AGGREGATE_EXECUTION_MODE=gpu_native_tolerant

# Point this at the SF100 Parquet directory on local NVMe.
export ALGEON_PARQUET_DIR=/mnt/algeon-nvme/algeon/fixture/tpcds/sf100/parquet

bash scripts/dev/bench_one.sh tpcds all --engine cpu_datafusion \
  --scale 100 --warmups 1 --iterations 1 \
  --parquet-dir "$ALGEON_PARQUET_DIR" --out /tmp/tpcds-cpu.tsv
bash scripts/dev/bench_one.sh tpcds all --engine native_gpu \
  --scale 100 --warmups 1 --iterations 1 \
  --parquet-dir "$ALGEON_PARQUET_DIR" --out /tmp/tpcds-gpu.tsv
```

`native_tpcds_parity_report` checks the result values. It runs each query on
both paths in one process, with the CPU side on the same partition and batch
settings, and compares every value. A top-level `ORDER BY` preserves the
sequence of sorting keys. Rows may exchange positions only within contiguous
groups equal on every key; unresolved keys retain emitted row order. Queries
without top-level ordering use multiset comparison, preserving duplicate
counts. Tie groups require exact key equality. Floating-point
columns, which are the GPU variance and standard deviation outputs under
`gpu_native_tolerant`, accept an absolute and relative error of
<code>{String(tpcdsSf100Benchmark.config.parity.floatToleranceAbsolute)}</code>;
every other column must match exactly. The result-values column in the table
names the mode used for each query.

```bash
export ALGEON_TPCDS_PARITY_FLOAT_ABS_TOLERANCE=0.00000001
export ALGEON_TPCDS_PARITY_FLOAT_REL_TOLERANCE=0.00000001
flock /tmp/cudf-gpu.lock cargo run --release -p bench --all-features \
  --bin native_tpcds_parity_report > /tmp/tpcds-parity.tsv
```

The generator refuses a parity TSV whose dataset root, query set or CPU
settings differ from the timing run:

```bash
python3 website/scripts/generate_tpcds_sf100_benchmark_ts.py \
  --cpu-tsv /tmp/tpcds-cpu.tsv --gpu-tsv /tmp/tpcds-gpu.tsv \
  --parity-tsv /tmp/tpcds-parity.tsv \
  --environment /tmp/tpcds-environment.json \
  --out website/src/data/tpcdsSf100Benchmark.ts
```

### Concurrent TPC-H streams through algeon_server

The runs above time one query at a time inside a benchmark process. In this
run, `algeon_server` served the 22 TPC-H SF100 queries to 1 to 16 concurrent
Flight SQL clients on the same g7e.8xlarge. Each client ran one stream: the 22
queries in its own seeded order, twice, with the first pass as warm-up. The
GPU server ran every query in `native_required` mode. The CPU path is the same
binary with `execution_mode = "functions_only"`, which plans every query
through DataFusion on the CPU. Queries that call GPU UDTFs go through the same
admission queue and memory caps; this run uses relational SQL only.

<ServerLoadBenchmark />

With the server's default settings, the GPU completed
{gpuSeries(2).peak.completedQps.toFixed(2)} queries per second
({Math.round(gpuSeries(2).peak.completedQps * 3600).toLocaleString('en-US')} per
hour) at {gpuSeries(2).peak.streams} streams. More streams added latency
without adding throughput. The CPU path peaked at
{cpuSeries.peak.completedQps.toFixed(2)} queries per second, and the GPU
default completed {(gpuSeries(2).peak.completedQps / cpuSeries.peak.completedQps).toFixed(1)}
times as many.

The admission setting `max_active_attempts` (A below) sets where throughput
levels off. A GPU runs at most A queries at once and holds later ones in a
FIFO queue. Each admitted query gets a fixed memory cap, the device's managed
capacity divided by A: {gib(gpuSeries(1).queryLimitBytes)} GiB at A=1,
{gib(gpuSeries(2).queryLimitBytes)} GiB at the default A=2 and
{gib(gpuSeries(3).queryLimitBytes)} GiB at A=3 on this GPU. A=1 stayed near
{gpuSeries(1).peak.completedQps.toFixed(2)} queries per second from two
streams up. A=3 reached {gpuSeries(3).peak.completedQps.toFixed(2)},
{Math.round((gpuSeries(3).peak.completedQps / gpuSeries(2).peak.completedQps - 1) * 100)}%
above the default. All 22 queries completed under each of the three caps. A
query that allocates more than its cap fails with `query_memory_limit_exceeded`
while the other admitted queries continue. Raising A therefore raises
throughput for queries that fit the smaller cap and lowers the largest query
the server can run. [Memory and query lifetime](../../design/admission.mdx)
describes the queue, the caps and how the allocator enforces them.

<details>
<summary>Server overload behavior (load above capacity)</summary>

In the overload runs, the client submitted queries to the default
configuration at a fixed rate for five minutes after 30 seconds of warm-up. It
sent each query on schedule whether or not earlier ones had finished, picking
among the 22 queries with a seeded draw. C below is the default configuration's
highest median throughput, {serverLoadBenchmark.overload.capacityQps.toFixed(2)}
queries per second. Values are medians of
{serverLoadBenchmark.config.overloadRepeats} runs.

<ServerLoadOverloadTable />

Completed throughput held between 1.6 and 1.7 queries per second when the
offered rate doubled. The server rejected the excess with `service_overloaded`.
A query that found all {serverLoadBenchmark.config.maxQueuedAttempts} queue
places taken received it after a median 49 ms. A queued query that had not
started within `max_queue_wait_ms` ({serverLoadBenchmark.config.maxQueueWaitMs / 1000} s)
received it when the wait expired. Accepted queries at 1.5 × C and above waited in a
full queue before running, and their p95 latency rose to 32 s. Every accepted
result matched the CPU reference. After each run the server reported no active
queries and no granted memory.

</details>

<details>
<summary>Server load measurement methodology and reproduction</summary>

- Client and server ran on one machine over loopback. `taskset` pinned the
  client to {serverLoadBenchmark.environment.clientCpuThreads} vCPUs and the
  server to the other {serverLoadBenchmark.environment.serverCpuThreads}. The
  Parquet files were fully resident in the page cache before each run.
- The server is a release build of commit
  <code>{serverLoadBenchmark.environment.sourceRevision.slice(0, 12)}</code>.
  The default configuration is
  [`tpch-sf100-server.toml`](https://github.com/algeon-dev/algeon/blob/main/crates/tools/fixtures/stress/tpch-sf100-server.toml),
  which sets only `native_required` and the table registrations. A=1 and A=3
  add one `[[admission.device_profiles]]` entry. The CPU path ran with
  `datafusion.execution.target_partitions = 32` and
  `datafusion.execution.batch_size = 32768`.
- Each point is the median of {serverLoadBenchmark.config.repeats} runs, with
  a fresh server for each run. Throughput counts queries completed in the
  measured pass, from the moment every stream finished warm-up to the last
  completion. Latency runs from `GetFlightInfo` to the last result batch.
- Every result was compared with references recorded by the CPU path.
  {serverLoadBenchmark.summary.gpuResultsMatched.toLocaleString('en-US')} GPU
  results matched, warm-up passes included. Q11 returns no rows at SF100
  because the DuckDB query text fixes its `FRACTION` at 0.0001 where the
  specification uses 0.0001 / SF; its check compares only the schema.
- This run is derived from TPC-H and is not a TPC-H Throughput Test. It runs
  no refresh functions, orders each stream from seed
  {serverLoadBenchmark.config.seed} and reports no TPC metric.
- The [stress runbook](https://github.com/algeon-dev/algeon/blob/main/crates/tools/fixtures/stress/RUNBOOK.md#tpc-h-sf100-streams)
  documents the server, reference, streams and overload commands for
  `algeon_tools flight-sql-stress`.

</details>
