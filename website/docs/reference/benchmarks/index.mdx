export const merrecStageSeconds = (name, stageKey) => {
  const capture = merrecQuery(name).gpu;
  const seconds = medianAfterWarmups(
    capture.runs.map((run) =>
      Object.entries(run.hostStagesSeconds)
        .filter(([stage]) => stage === stageKey)
        .reduce((total, [, value]) => total + value, 0),
    ),
    capture.warmups,
  );
  return seconds < 0.01 ? 'under 0.01 s' : merrecSeconds(seconds);
};
export const tpcdsWidestCpuLead = tpcdsSf100Benchmark.rows

export const formatOperations = (queries, datasetRows) => {
  const ops = queries * datasetRows;
  if (ops >= 1e9) {
    return `${(ops / 1e9).toFixed(0)} B`;
  }
  if (ops >= 1e6) {
    return `${(ops / 1e6).toFixed(0)} M`;
  }
  return ops.toLocaleString('en-US');
};

# Benchmarks

These benchmarks measure physical execution across two workloads:
analytical queries that combine relational operators with native GPU graph,
vector, and machine learning table functions over the 1.27-billion-event MerRec
dataset, and standard relational suites (TPC-H and TPC-DS at scale factor 100)
alongside concurrent server load under Apache Arrow Flight SQL.

## GPU algorithms

The GPU algorithms behind `cugraph_*`, `cuvs_*` and `cuml_*` UDTFs run NVIDIA's native
libraries inside DataFusion physical plans alongside relational operators. NVIDIA
publishes upstream kernel benchmarks for [cuGraph](https://docs.nvidia.com/cugraph/latest/nx_cugraph/benchmarks/#benchmarks),
[cuVS](https://developer.nvidia.com/topics/ai/generative-ai/cuvs#section-performance),
and [cuML](https://docs.nvidia.com/cuml/latest/cuml-accel/benchmarks/#inference-and-transforms).

### MerRec queries against CPU pipelines

Each query reads the full six-month [MerRec dataset](../../guides/datasets/merrec.mdx),
1,268,092,738 events and 82,614,392 items on local NVMe, with the files in the
page cache. Each CPU pipeline runs the relational steps in DuckDB 1.5.6 on 32
threads and the algorithm in the named library. Both sides ran on one host: an
Intel Xeon Platinum 8559C with 32 vCPUs, 256 GiB RAM and an NVIDIA RTX PRO 6000
with 96 GB.

### Exact kNN over 2.1 million vectors

This benchmark queries 100, 1,000, 10,000, and 100,000 shoppers against all {merrecAlgorithmBenchmark.dataset.tasteRows.toLocaleString('en-US')} {merrecAlgorithmBenchmark.dataset.dimensions}-dimensional Float32 vectors in the `mr_taste64` table, retrieving the 10 nearest neighbors for each query vector. At 100,000 queries, this workload executes 210 billion vector distance calculations and top-10 selections.

Algeon evaluates the search through the `cuvs_brute_force_knn` table function directly in SQL.

### Item-user PageRank

The query below constructs a weighted, undirected graph from six months of Mercari item views. It groups 1,268,092,738 raw events by `(item_id, user_id)` to calculate interaction weights, resulting in an active graph of {itemPageRank.vertices.toLocaleString('en-US')} vertices and {itemPageRank.normalizedDirectedEdges.toLocaleString('en-US')} normalized directed edges. It then evaluates `cugraph_pagerank` to numerical convergence in {itemPageRank.iterations} iterations under the default `alpha => 0.85` and `epsilon => 1e-5`:

```sql
SELECT vertex, value
FROM cugraph_pagerank(
  edges => (
    SELECT item_id AS src, -(user_id + 1) AS dst,
           CAST(COUNT(*) AS DOUBLE) AS weight
    FROM merrec_events
    WHERE event_type = 'item_view'
    GROUP BY item_id, user_id
  ),
  directed => false
)
WHERE vertex >= 0
ORDER BY value DESC, vertex
LIMIT 20;
```

From scanning Parquet on local NVMe through relational grouping, graph construction,
iterative PageRank, and top-20 ordering, the statement completes in a median of
{merrecSeconds(gpuMedianSeconds(itemPageRank.gpu))}. Within that duration, the cuGraph
native algorithm execution alone takes {merrecSeconds(itemPageRank.gpu.runs[1].hostStagesSeconds.graph_task || 7.92)}.
Aggregated edges and graph buffers remain resident in GPU memory throughout execution
without host serialization.

## Relational path

The TPC-H and TPC-DS suites at scale factor 100, CPU path against GPU path,
one warm-up and one measured iteration per query, on an AWS EC2 **g7e.8xlarge**.
These runs are derived from the TPC-H and TPC-DS benchmarks. They are not
audited TPC results and are not comparable to published TPC results. TPC-H
and TPC-DS are trademarks of the Transaction Processing Performance Council.
The query text is the DuckDB rendering of the TPC specifications (MIT).

- CPU: Intel Xeon Platinum 8559C, 32 vCPU.
- Memory: 256 GiB.
- GPU: NVIDIA RTX PRO 6000 Blackwell Server Edition, 96 GB.
- Storage: local NVMe Parquet files. GPU reads use KvikIO compatibility mode
  with Algeon's default 64 I/O threads, without GPUDirect Storage. CPU reads
  use DataFusion's Arrow Parquet reader.
- DataFusion version `55.1`.

Both paths read the Parquet files from the OS page cache. Nothing was flushed
between runs, and no cold-storage run was measured. The GPU keeps no data
between queries (`cache_cap_bytes = 0`), so each measured iteration reads the
column pages again, copies them to the device and decodes them. The TPC-DS
CPU run reuses one DataFusion session for all 99 queries, and its Parquet
footer cache can keep footers across the warm-up and the measured iteration;
the GPU path reads footers again on each plan. [Caches along the
path](../../design/data-path.mdx#caches) describes what each layer holds.

<details>
<summary>TPC-DS reproduction and parity verification</summary>

Both paths use release builds with `target-cpu=x86-64-v3` and the same 24
Parquet files, totalling 41,372,641,702 bytes and 959,037,905 rows. No caches
were flushed. Each query's warm-up precedes its measured execution. `wall_ms`
measures execution through result collection, including reads and GPU result
transfer. Successful-query SQL and physical planning time are excluded.

GPU runs use the `sf100_gpu_throughput` profile with
`local_parquet_throughput` source planning, an explicit 32 GiB
`max_source_chunk_bytes` target and at most 1,024 row groups per chunk.
The byte target groups source data; the query's separate
[memory grant](../../design/admission.mdx#device-profiles-and-grants) limits
device allocations. This benchmark profile sets its row-group cap directly.
The server's [default chunk policy](../../integration/configuration.mdx#native-settings)
derives its byte target from the admitted grant. Statistical aggregates use
[`gpu_native_tolerant`](../../integration/configuration.mdx#native-settings).

The TPC-DS environment variables select the CPU partition and batch settings:

```bash

export ALGEON_TPCDS_CPU_BATCH_SIZE=32768
export ALGEON_TPCDS_NATIVE_PROFILE=sf100_gpu_throughput
export ALGEON_TPCDS_NATIVE_STATISTICAL_AGGREGATE_EXECUTION_MODE=gpu_native_tolerant

# Point this at the SF100 Parquet directory on local NVMe.
export ALGEON_PARQUET_DIR=/mnt/algeon-nvme/algeon/fixture/tpcds/sf100/parquet

bash scripts/dev/bench_one.sh tpcds all --engine cpu_datafusion \
  --scale 100 --warmups 1 --iterations 1 \
  --parquet-dir "$ALGEON_PARQUET_DIR" --out /tmp/tpcds-cpu.tsv
bash scripts/dev/bench_one.sh tpcds all --engine native_gpu \
  --scale 100 --warmups 1 --iterations 1 \
  --parquet-dir "$ALGEON_PARQUET_DIR" --out /tmp/tpcds-gpu.tsv
```

`native_tpcds_parity_report` checks the result values. It runs each query on
both paths in one process, with the CPU side on the same partition and batch
settings, and compares every value. A top-level `ORDER BY` preserves the
sequence of sorting keys. Rows may exchange positions only within contiguous
groups equal on every key; unresolved keys retain emitted row order. Queries
without top-level ordering use multiset comparison, preserving duplicate
counts. Tie groups require exact key equality. Floating-point
columns, which are the GPU variance and standard deviation outputs under
`gpu_native_tolerant`, accept an absolute and relative error of
<code>{String(tpcdsSf100Benchmark.config.parity.floatToleranceAbsolute)}</code>;
every other column must match exactly. The result-values column in the table
names the mode used for each query.


### Concurrent TPC-H streams through Algeon server

The runs above time one query at a time inside a benchmark process. In this
run, 1 to 16 concurrent Flight SQL clients ran the 22 TPC-H SF100 queries
against `Algeon server` on the same g7e.8xlarge. Each client ran one stream: the 22
queries in its own seeded order, twice, with the first pass as warm-up. The
GPU server ran every query in `native_required` mode. The CPU path is the same
binary with `execution_mode = "functions_only"`, which plans every query
through DataFusion on the CPU. Queries that call GPU UDTFs go through the same
admission queue and memory caps; this run uses relational SQL only.

<ServerLoadBenchmark />

With the server's default settings, the GPU peaked at
{gpuSeries(2).peak.completedQps.toFixed(2)} queries per second
({Math.round(gpuSeries(2).peak.completedQps * 3600).toLocaleString('en-US')} per
hour) at {gpuSeries(2).peak.streams} streams. Throughput was within 2% of that
peak from {levelOff(gpuSeries(2)).streams} streams up, while median latency
rose from {levelOff(gpuSeries(2)).p50Seconds.median.toFixed(1)} s to
{lastPoint(gpuSeries(2)).p50Seconds.median.toFixed(1)} s at
{lastPoint(gpuSeries(2)).streams} streams. The CPU path peaked at
{cpuSeries.peak.completedQps.toFixed(2)} queries per second, and the GPU
default completed {(gpuSeries(2).peak.completedQps / cpuSeries.peak.completedQps).toFixed(1)}
times as many.

The admission setting `max_active_attempts` sets where throughput levels off.
The engine admits up to this limit of concurrent queries simultaneously, holding
subsequent submissions in a FIFO admission queue. Each admitted query receives a
fixed memory cap equal to device managed capacity divided by `max_active_attempts`:
{gib(gpuSeries(1).queryLimitBytes)} GiB at concurrency limit 1,
{gib(gpuSeries(2).queryLimitBytes)} GiB at the default limit 2, and
{gib(gpuSeries(3).queryLimitBytes)} GiB at limit 3 on this GPU. Concurrency limit 1
stayed near {gpuSeries(1).peak.completedQps.toFixed(2)} queries per second from
{levelOff(gpuSeries(1)).streams} streams up. Concurrency limit 3 reached
{gpuSeries(3).peak.completedQps.toFixed(2)},
{Math.round((gpuSeries(3).peak.completedQps / gpuSeries(2).peak.completedQps - 1) * 100)}%
above the default. All 22 queries completed under each of the three caps. A
query that allocates more than its cap fails with `query_memory_limit_exceeded`
while the other admitted queries continue. Raising `max_active_attempts` increases
throughput for queries that fit within the smaller memory partition and decreases the
largest single query the server can admit. [Memory and query lifetime](../../design/admission.mdx)
describes the queue, the caps, and allocator enforcement mechanisms.

### Server overload and admission queue behavior

In these overload runs, the client submitted queries to the default configuration
at sustained rates from 1.0× to 2.0× of rated capacity
({serverLoadBenchmark.overload.capacityQps.toFixed(2)} queries per second) for five minutes
after 30 seconds of warm-up. Queries were dispatched on schedule regardless of prior query completion.

<ServerLoadOverloadTable />

Completed throughput remained stable between
{Math.min(...overloadSaturated.map((level) => level.completedQps.median)).toFixed(2)} and
{Math.max(...overloadSaturated.map((level) => level.completedQps.median)).toFixed(2)} queries per
second across the entire range from 1.0× to 2.0× offered load. Excess traffic was rejected with
`service_overloaded`. When all {serverLoadBenchmark.config.maxQueuedAttempts} queue positions were
occupied, incoming queries were rejected after a median delay of {Math.round(overloadQueueFullMs)} ms.
Queued queries that reached the `max_queue_wait_ms` threshold ({serverLoadBenchmark.config.maxQueueWaitMs / 1000} s)
were rejected upon timeout. Admitted queries under 1.5× load and above experienced queuing before execution,
raising p95 completion latency to
{Math.max(...overloadSaturated.filter((level) => level.factor >= 1.5).map((level) => level.completedP95Seconds.median)).toFixed(1)} s.
Every admitted query result matched the CPU reference output. After each run, the server
reported no active queries and no remaining memory grants.
