# Benchmarks

The MerRec queries compare Algeon with CPU pipelines over the
1.27-billion-event dataset. The TPC-H suite at scale factors 100 and 500 and the
TPC-DS suite at scale factor 100 compare the CPU and GPU paths, and the server
load runs drive concurrent TPC-H streams through Arrow Flight SQL.

## GPU algorithms

The GPU algorithms behind `cugraph_*`, `cuvs_*` and `cuml_*` UDTFs run NVIDIA's native
libraries inside DataFusion physical plans alongside relational operators. NVIDIA
publishes upstream kernel benchmarks for [cuGraph](https://docs.nvidia.com/cugraph/latest/nx_cugraph/benchmarks/#benchmarks),
[cuVS](https://developer.nvidia.com/topics/ai/generative-ai/cuvs#section-performance),
and [cuML](https://docs.nvidia.com/cuml/latest/cuml-accel/benchmarks/#inference-and-transforms).

### MerRec queries against CPU pipelines

Each query reads the full six-month [MerRec dataset](../../guides/datasets/merrec.mdx),
1,268,092,738 events and 82,614,392 items on local NVMe, with the files in the
page cache. Each CPU pipeline runs the relational steps in DuckDB 1.5.6 on 32
threads and the algorithm in the named library. Both sides ran on one host: an
Intel Xeon Platinum 8559C with 32 vCPUs, 256 GiB RAM and an NVIDIA RTX PRO 6000
with 96 GB.

### Item-user PageRank

The query below builds a weighted, undirected graph from six months of item
views. It scans the 1,268,092,738 events, groups the item views by
`(item_id, user_id)` for the interaction weights, and runs `cugraph_pagerank`
over the resulting {itemPageRank.vertices.toLocaleString('en-US')} vertices and
{itemPageRank.normalizedDirectedEdges.toLocaleString('en-US')} directed edges.
PageRank converges in {itemPageRank.iterations} iterations at the default
`alpha => 0.85` and `epsilon => 1e-5`.

```sql
SELECT vertex, value
FROM cugraph_pagerank(
  edges => (
    SELECT item_id AS src, -(user_id + 1) AS dst,
           CAST(COUNT(*) AS DOUBLE) AS weight
    FROM merrec_events
    WHERE event_type = 'item_view'
    GROUP BY item_id, user_id
  ),
  directed => false
)
WHERE vertex >= 0
ORDER BY value DESC, vertex
LIMIT 20;
```

The whole query, edge preparation included, takes a median of
{merrecSeconds(gpuMedianSeconds(itemPageRank.gpu))}; the cuGraph PageRank call
accounts for {merrecSeconds(itemPageRankGraphSeconds)} of it. The aggregated
edges and the graph stay in device memory between the `GROUP BY` and the
PageRank call.

## Relational path

The TPC-H suite on three datasets and the TPC-DS suite at scale factor 100,
CPU path against GPU path, on an AWS EC2 **g7e.8xlarge**.
Both suites were measured on {relationalDates} at revision
<code>{relationalRevision}</code>, the build of the server load runs below.
These runs are derived from the TPC-H and TPC-DS benchmarks. They are not
audited TPC results and are not comparable to published TPC results. TPC-H
and TPC-DS are trademarks of the Transaction Processing Performance Council.
The query text is the DuckDB rendering of the TPC specifications (MIT), with
Q11's `FRACTION` substituted as the specification defines it, 0.0001 / SF.

Each query ran {timing.warmups} warm-up and {timing.iterations} measured iterations on each
path, and the tables and charts report the median measured iteration.
A measured time starts when the query text is passed to `SessionContext::sql`
and ends when the last result batch has been collected. It covers SQL parsing,
logical optimization, physical planning and execution; DataFusion's `dfbench`
times its TPC-H runs over the same span. Session construction and table
registration run before the timer starts.

- CPU: Intel Xeon Platinum 8559C, 32 vCPU.
- Memory: 256 GiB.
- GPU: NVIDIA RTX PRO 6000 Blackwell Server Edition, 96 GB.
- Storage: local NVMe Parquet files. GPU reads use KvikIO compatibility mode
  with Algeon's default 64 I/O threads, without GPUDirect Storage. CPU reads
  use DataFusion's Arrow Parquet reader.
- DataFusion version `55.1`.

Both paths read the Parquet files through the OS page cache. Before each
dataset ran, the other datasets' files were evicted from the cache, and the
resident share of the dataset's own files, by bytes, was recorded:
{tpchDatasets.map((dataset) => `${dataset.label} ${residency(dataset.pageCache)}`).join('; ')};
TPC-DS {residency(tpcdsSf100Benchmark.pageCache)}. The SF500 files total
{gib(tpchDataset('sf500_sorted').pageCache.totalBytes)} GiB on a host with 256 GiB of memory,
which also holds the CPU path's working set. No cold-storage run was measured.
The GPU keeps no data between queries (`cache_cap_bytes = 0`), so each measured
iteration reads the column pages again, copies them to the device and decodes
them. Each TPC-H query ran in its own process and built a new session for every
iteration. The TPC-DS CPU and GPU runs each reuse one DataFusion session for all
99 queries, so planning on either path can find a file's footer in the
session's metadata cache from the warm-up; the GPU path's cuDF reader still
parses the footer of each file it reads once per query. [Caches along the
path](../../design/data-path.mdx#caches) describes what each layer holds.

Both paths use release builds with `target-cpu=x86-64-v3`. The TPC-DS runs use
the same {tpcdsSf100Benchmark.dataset.fileCount} Parquet files,

derives its byte target from the admitted grant. Statistical aggregates use
[`gpu_native_tolerant`](../../integration/configuration.mdx#native-settings).

### Concurrent TPC-H streams through Algeon server

The runs above time one query at a time inside a benchmark process. In this
run, 1 to 16 concurrent Flight SQL clients ran the 22 TPC-H SF100 queries
against `Algeon server` on the same g7e.8xlarge. Each client ran one stream: the 22
queries in its own seeded order, twice, with the first pass as warm-up. The
GPU server ran every query in `native_required` mode. The CPU path is the same
binary with `execution_mode = "functions_only"`, which plans every query
through DataFusion on the CPU. Queries that call GPU UDTFs go through the same
admission queue and memory caps; this run uses relational SQL only.
