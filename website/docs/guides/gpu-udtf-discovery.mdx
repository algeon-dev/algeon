# Discover & Validate GPU UDTFs

Use this guide before adding a cuGraph, cuVS, or cuML UDTF to a query. It follows
the same sequence for embedded sessions and Flight SQL: list what this build
can run, inspect one UDTF's contract, validate the call statically, execute it,
then check the complete query before production use.

This page shows the workflow only. For every returned column, JSON schema, and
validation-envelope rule, see the
[GPU UDTF Catalog API](../reference/gpu-udtf-catalog.mdx).

## 1. List installed UDTFs

Start with the UDTFs available in the current build and session. Filter by
provider when you already know the workload:

<CodeBlock language="sql">{catalog.list.sql}</CodeBlock>

<Details summary="Example response">
<Table>
<thead><tr><th>function_name</th><th>provider</th><th>available</th><th>summary</th></tr></thead>
<tbody>{catalog.list.rows.map(row => <tr key={row.function_name}><td><code>{row.function_name}</code></td><td>{row.provider}</td><td>{String(row.available)}</td><td>{row.summary}</td></tr>)}</tbody>
</Table>
</Details>

`available=true` means the UDTF can be planned for GPU execution in this
build and session. It does not prove that a surrounding query runs entirely
on the GPU. Step 5 covers that. cuVS UDTFs require the `cuvs` feature, and
`cuml_forest_predict` requires a
[models root](../integration/configuration.mdx#models-and-forest-inference).

## 2. Describe the selected UDTF

Retrieve the canonical signature, relation roles, option schema, output schema,
and lifecycle limits before constructing a call:

~~~sql
SELECT signature, relation_roles_json, options_schema_json, result_schemas_json, limitations_json
FROM gpu_describe_function('cugraph_pagerank');
~~~

<Details summary="Example response">
<CodeBlock language="json">{asJson(Object.fromEntries(described.map(column => [column, pagerank[column]])))}</CodeBlock>
</Details>

UDTF names are exact canonical names. The returned descriptor is useful
when a client or agent needs to construct SQL dynamically, while the provider
UDTF pages explain the same contract in task-specific terms.

## 3. Validate a concrete call

Validate registered relation metadata and the provider-owned options before
execution:

<CodeBlock language="sql">{catalog.valid_call.sql}</CodeBlock>

<Details summary="Example response · valid call">
<CodeBlock language="json">{asJson(catalog.valid_call.rows[0])}</CodeBlock>
</Details>

This is static validation: it checks the named tables' or views' schemas and
the options, reads no data, and runs nothing on the GPU. Only registered
tables or views resolve, and each one must already expose the role's canonical
columns (`src`/`dst` for cuGraph edges, `id` plus feature columns for cuVS
relations). A call whose relation aliases, filters, joins, or reads a CTE is
not represented by this envelope. Run `EXPLAIN GPU` on the final SQL instead,
or register that derived relation as a view and validate the view.

A rejected call also returns one row:

<CodeBlock language="sql">{catalog.rejected_call.sql}</CodeBlock>

<Details summary="Example response · rejected call">
<CodeBlock language="json">{asJson(catalog.rejected_call.rows[0])}</CodeBlock>
</Details>

`message` lists every problem found in one pass. `error_code` and
`details_json` locate the first.

## 4. Execute with the provider's relation syntax

While the discovery and validation interfaces are identical across providers,
execution syntax reflects each library's relation roles:

- cuGraph passes graph topologies via named relation subqueries (e.g.,
  `edges => (SELECT src, dst FROM edges)`).
- cuVS and cuML pass vector and training relations as named subqueries
  alongside scalar options (e.g., `input => (SELECT ...)`, `k => 10`).

Use the [cuGraph UDTFs](../cugraph/udtfs/index.mdx),
[cuVS UDTFs](../cuvs/udtfs/index.mdx), and
[cuML UDTFs](../cuml/udtfs/index.mdx) pages for each UDTF's signature,
input contract, outputs, and lifecycle.

## 5. Check whole-query GPU coverage

gpu_validate_call covers one selected UDTF call. It does not inspect
DataFusion operators, sources, or host boundaries feeding and consuming that
call. Before shipping a composed query, use
[GPU coverage validation](../integration/gpu-coverage-validation.mdx) to check
the final planned path.
