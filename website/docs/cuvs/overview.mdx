# cuVS SQL API (WIP)

Algeon exposes NVIDIA RAPIDS
[**cuVS**](https://github.com/NVIDIA/cuvs) as SQL table functions over
DataFusion SQL sessions, following the pattern already used by the
[cuGraph SQL API](../cugraph/overview.mdx). Each `cuvs_*` function reads a
relation of vectors, runs a GPU vector operation, and returns rows you can join
and filter alongside the rest of your query, over the data already in your
session, with no separate vector store and no copy to keep in sync.

Six functions are available: exact brute-force kNN (`cuvs_brute_force_knn`),
query-local approximate IVF-Flat search (`cuvs_ivf_flat`), pairwise distances
(`cuvs_pairwise_distance`), per-row vector selection (`cuvs_top_k`),
KMeans clustering (`cuvs_kmeans`), and PCA (`cuvs_pca`). They execute on
GPU when the prerequisites in [Execution](#execution) are met. Persistent
indexes are not exposed.

The function registry, JSON schemas, and generated pages below come from the
same live metadata API exposed to embedded and Flight SQL clients.

## Vector input and call shape

Every `cuvs_*` execution relation is a parenthesized `SELECT` subquery. The
relation remains an explicit planner child, so it can use ordinary session
tables, views, CTEs, Parquet scans, Iceberg tables, or a preceding SQL result.
Bare table identifiers and quoted table-name strings are not execution inputs.

For metadata-only validation, `gpu_validate_call` instead resolves a named
registered table or view and checks its schema without scanning rows or
invoking the GPU. [Vector Inputs](./vector-inputs.mdx) documents relation
identity, dense-vector binding shapes, and the validation-versus-runtime
boundary.

## Execution

Use [functions-only execution](../integration/datafusion-session.mdx#choose-an-execution-mode)
to keep input subqueries and surrounding SQL on DataFusion CPU while vector
operations run on GPU. That mode retains the prerequisites below and uses
bounded, non-spilling host staging for CPU inputs.

A `cuvs_*` call runs on the GPU when all of the following hold:

1. the binary was built with the `cuvs` feature (otherwise every call returns a
   structured `required_feature_disabled` error, and `gpu_list_functions`
   reports the family as unavailable);
2. the session installed cuVS SQL: embedded sessions chain
   `try_with_cuvs_sql()` as shown in
   [DataFusion Session](../integration/datafusion-session.mdx#add-cugraph-and-cuvs-sql),
   and the Flight SQL server installs it on every session it builds;
3. a `AlgeonGpuBackend` is installed, because execution needs an admitted query
   memory domain.

`gpu_validate_call` validates schemas and options without scanning relations or
executing GPU work. At runtime, `cuvs_*` calls use the admitted query memory
domain, and its allocator enforces the configured cap; an input that does not
fit that cap fails with a typed allocation error rather than spilling.

cuVS SQL has no persistent cross-statement cache for brute-force or IVF-Flat
indexes, KMeans models, PCA transforms, or result relations. Pairwise distances
and Top-K selections likewise produce query-local results. Exact kNN and
IVF-Flat each build and destroy an index within one evaluated statement.
KMeans fits its model, and PCA fits and transforms its input.

The server's source and graph caches do not cache cuVS artifacts. See
[Configuration](../integration/configuration.mdx) for server cache configuration
and bounded memory limits.
