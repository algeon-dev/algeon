## Compose algorithms {/* #from-a-question-to-a-working-set */}

Each example above passes a subquery to a GPU UDTF (user-defined table
function) and gets rows back. SQL groups those rows, joins them to titles or
file metadata, or hands them to another UDTF. In the marketplace example, the product groups
ranked by personalized PageRank become the vertex pairs that Jaccard scores,
inside the same statement.

SQL filters and joins select the input rows. The size of that input depends
on the data and conditions, and each UDTF requires specific columns and
types. GPU memory also includes graph construction and algorithm scratch space.

## Algorithm families {/* #available-building-blocks */}

DataFusion provides SQL planning and the session APIs. Algeon adds cuDF
execution for supported relational plans and GPU UDTFs backed by
NVIDIA's GPU libraries:

| Capability | SQL interface | Current use |
| --- | --- | --- |
| Graph analysis | [`cugraph_*`](./cugraph/overview.mdx) | Graph traversal, centrality, community detection, components, similarity, core structure, and ForceAtlas2 layout. |
| Vector analysis | [`cuvs_*`](./cuvs/overview.mdx) | Exact and approximate kNN, pairwise distances, per-row top-k, KMeans, and PCA over vector columns. |
| Machine learning | [`cuml_*`](./cuml/overview.mdx) | Fit models within a query, or score features with a pretrained XGBoost, LightGBM, or Treelite forest. |

All of them return ordinary rows, and each family's UDTF index lists
every installed UDTF. Each family requires its build feature and
session setup; pretrained forest inference also requires a configured models
directory. General inference for neural networks trained in PyTorch remains
future work.

## Build and run {/* #start-exploring */}

Algeon supports Linux with an NVIDIA GPU. Follow [Build & Test](./build/overview.md)
for prerequisites and build instructions, then choose an integration:

- **Rust application:** install Algeon in an [embedded DataFusion session](./integration/datafusion-session.mdx).
- **SQL client:** run the [Arrow Flight SQL server](./integration/flight-sql-server.mdx) and connect with ADBC.

The [demo dataset guides](./guides/datasets/index.mdx) prepare and register the
tables behind the examples above. [Introducing Algeon](/blog/introducing-algeon)
describes the project's motivation and application scenarios.

## DataFusion integration {/* #how-it-fits-into-datafusion */}

<ArchitectureDiagram
  caption={<>A query enters through the interface you already use. Algeon's
  DataFusion optimizer rule replaces supported plan candidates with GPU
  execution in the same process, and results return to that interface as
  ordinary Arrow batches. The lower arrows show where table data comes from:
  Parquet files on local disk or in S3-compatible object storage.</>}
/>

The [execution mode](./integration/datafusion-session.mdx#choose-an-execution-mode)
is configured on the shared backend before sessions are installed and sets
how much relational work joins the GPU:

| Mode | Relational execution |
| --- | --- |
| `native_preferred` (default) | Supported candidates run on cuDF; unsupported or unselected candidates keep their DataFusion CPU plan with the same results. |
| `functions_only` | Ordinary SQL runs on DataFusion CPU around explicit GPU UDTFs. |
| `native_required` | A completed plan that still contains DataFusion CPU operators is rejected. |

Selection first tries to replace the
[whole query](./design/native-lowering.mdx#selection-fallback-and-mixed-execution);
when it does not lower, supported subtrees below the operators that stay on
DataFusion run as [native fragments](./reference/glossary.md#planning-and-lowering). Explicit
GPU UDTFs have no CPU fallback in any mode, and once GPU execution
starts, a failure returns as a structured error and is never replayed on
CPU. In `functions_only`, inputs crossing from CPU operators to a GPU
UDTF are staged in host memory before upload, under
[host staging limits](./integration/datafusion-session.mdx#compose-cpu-and-gpu-work)
separate from the GPU cap.

## Validate and diagnose {/* #context-for-the-next-attempt */}

[Discover & Validate GPU UDTFs](./guides/gpu-udtf-discovery.mdx) covers
UDTF discovery, signatures, and static validation against registered tables
or views. Static validation reads no rows and launches no kernels; checks that
depend on data happen during execution.
[GPU coverage reports](./integration/gpu-coverage-validation.mdx) describe which
parts of a query can run on the GPU without reserving device capacity or proving
that the query fits in memory. For execution failures,
[structured errors and attempt reports](./integration/handling-errors.mdx)
provide diagnostic fields and retry guidance.

## Execution boundaries

- DataFusion is the current integration. Embed Algeon in a Rust service or
  connect through Arrow Flight SQL. DuckDB is the next adapter direction under
  consideration and Spark a longer-term one; neither is supported today.
- GPU support covers a [subset of SQL](./reference/native-sql-support.mdx)
  and [data types](./reference/data-type-support.md). Nested and binary types
  and most list shapes stay on the CPU path.
- One GPU per query. Independent queries can be spread across configured
  GPUs, but a single query never spans devices.
- No spilling. Each query is admitted against a per-device memory ledger and
  runs inside a fixed
  [grant](./design/admission.mdx#device-profiles-and-grants) that its
  allocator enforces; exceeding it returns an allocation error. Graph
  construction and algorithm scratch space count toward the grant alongside
  input data; a small SQL input alone does not guarantee that an algorithm
  fits.
- GPU file scans read local and S3-compatible Parquet, read-only. The local
  workspace supports views and `CREATE TABLE AS` tables, whose results are
  collected in host memory and uploaded again by a later native scan; nothing writes
  back to a source catalog. Non-Parquet files stay on the DataFusion path, and
  [Iceberg tables](./integration/overview.mdx#iceberg-support) are not a
  supported source.
- Vector indexes and fitted models live within one statement, and pretrained
  forest inference reads its external model file for each statement. Graphs
  are also built within a statement, except that a bounded server can retain
  eligible constructed graphs under the
  [graph cache contract](./cugraph/overview.mdx#reuse-in-bounded-servers).
  The [cuOpt SQL API](./cuopt/overview.mdx) remains work in progress.
