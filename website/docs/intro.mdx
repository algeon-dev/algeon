# Welcome to DataFusion Nexus

**DataFusion Nexus makes [Apache DataFusion](https://datafusion.apache.org/)
run on the GPU.** It executes SQL with
[RAPIDS cuDF](https://docs.rapids.ai/api/cudf/stable/), adds
[cuGraph](https://docs.rapids.ai/api/cugraph/stable/) graph algorithms you can
call from SQL, and reads [Apache Iceberg](https://iceberg.apache.org/) and
Parquet data.

You can use it in two ways:

- **As a DataFusion session** — embed it in your own backend service.
  `NexusGpuBackend` installs GPU execution on DataFusion sessions while sharing
  one admission queue and GPU memory governor across concurrent requests. With
  the `cugraph` feature, add `with_cugraph_sql` for graph algorithms.
- **As a standalone server** — run the built-in Arrow Flight SQL server and connect from
  your backend with the Apache Arrow ADBC Flight SQL driver. See
  [Integrating Nexus](./integration/overview.mdx) to pick an integration surface or
  start a server.

## Features

- **GPU SQL execution.** The parts of a query that Nexus supports execute on
  cuDF. Under the default `GpuPreferred` policy, the remainder runs on the
  standard DataFusion CPU path, so an unsupported operator is a fallback rather
  than a failure.

- **Graph algorithms in SQL.** The `cugraph_*` table functions (PageRank,
  BFS, Louvain, ForceAtlas2, and others) behave like ordinary tables: point one
  at an edge table or view, then enrich the result. The
  [ForceAtlas2 examples](./cugraph/algorithms/layout/cugraph_force_atlas2.mdx#examples)
  are a good place to start.

- **Lakehouse data access.** Query Iceberg tables from REST catalogs, AWS Glue,
  or S3-compatible object stores. Remote catalogs remain read-only, while views
  and scratch tables can live in an opt-in mutable local workspace overlay.
- **Explainable planning.** Planning reports record which parts of a plan
  executed on the GPU, which fell back to CPU, and the reason for each. Errors
  carry stable codes and machine-readable facts rather than log messages alone.
  [GPU coverage validation](./integration/gpu-coverage-validation.mdx) turns
  this into a question you can ask before running a query:
  `SELECT * FROM nexus_explain_coverage('<sql>')` reports whether the planned
  path stays on the GPU and which operator, expression, type, or source forces
  CPU execution.
- **Bounded GPU memory.** Bounded mode plans each query against a GPU memory
  budget: shapes without a provable memory contract are rejected at planning
  time, and admitted queries receive their reservation before execution.
  Runtime memory pressure is absorbed by bounded chunk-split retries; a query
  that exhausts its retries fails with structured facts rather than an opaque
  OOM.

## How execution works

Nexus recognizes the query fragments it supports, lowers them into the
DataFusion-free `nexus-query-engine` plan, and executes them with cuDF.
Fragments it does not recognize remain on the standard DataFusion CPU path, and
a structured report records the reason. [Design](./design/index.mdx) describes this
boundary in detail.

## Current limitations

- **A subset of Arrow data types.** Native execution covers the common
  relational types — booleans, integers, floats, `Decimal128`, strings, dates,
  timestamps, and durations. Nested and binary types and most list shapes stay
  on the DataFusion CPU path; on Iceberg scans an unsupported projected type
  fails planning instead. [Data Type Support](./reference/data-type-support.md)
  lists the exact boundaries.
- **No cross-GPU communication.** Independent queries can be placed on different
  GPUs, but a single query cannot exchange data between GPUs.
- **Partial Iceberg merge-on-read.** Position deletes are applied natively, but
  not on a fast path. Equality deletes and delete vectors are unsupported:
  because Iceberg scans have no built-in CPU reader, planning fails with a
  structured error even under the default `GpuPreferred` policy. Serving such
  tables on the CPU requires the opt-in `iceberg-cpu` build and the
  `cpu_fallback` session profile, which reroutes every Iceberg table in the
  session.
- **Parquet only.** Parquet is the only supported data file format for now.
- **No Substrait input.** Queries enter as SQL text, through an embedded
  DataFusion session or Flight SQL; Nexus does not accept serialized query
  plans, and the Flight SQL server reports Substrait as unsupported to
  clients.

## Repository layout

The Cargo workspace has four members:

- `datafusion-nexus` — the DataFusion-facing adapter: optimizer rule, table
  functions, Iceberg integration, the Flight SQL server, and reports.
- `nexus-query-engine` — the DataFusion-free native plan and GPU executor.
- `datafusion-nexus-bench` — benchmark, report, fixture, and stress binaries.
- `datafusion-nexus-tools` — developer and operator tools, including local
  end-to-end runners.

Two sibling repositories are also first-class parts of the implementation,
even though they are not workspace members: `cudf-rs` is the Rust/libcudf
boundary used by the native executor, and `cugraph-rs` is the Rust/libcugraph
boundary behind the `cugraph_*` SQL functions.
