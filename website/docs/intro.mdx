# Welcome to DataFusion Nexus

DataFusion Nexus is a GPU query engine for
[Apache DataFusion](https://datafusion.apache.org/). It takes the physical plans
DataFusion already produces and executes the parts it supports on the GPU: SQL
runs on [Nvidia cuDF](https://docs.rapids.ai/api/cudf/stable/), graph algorithms
from [cuGraph](https://docs.rapids.ai/api/cugraph/stable/) are callable directly
from SQL, and data is read from [Apache Iceberg](https://iceberg.apache.org/)
and Parquet. Operators it does not support remain on the standard DataFusion CPU
path.

Nexus is designed to sit inside your own architecture. Graph workloads are
exposed as ordinary SQL table functions over your existing data, and planning
decisions and errors are returned as structured, machine-readable values — so
both application code and agents can reason about a query before and after it
runs.

## Features

- **GPU SQL execution.** The parts of a query that Nexus supports execute on
  cuDF. Under the default `GpuPreferred` policy, the remainder runs on the
  standard DataFusion CPU path, so an unsupported operator is a fallback rather
  than a failure.
- **Graph algorithms in SQL.** The `cugraph_*` table functions (PageRank, BFS,
  Louvain, ForceAtlas2, and more) run cuGraph over an edge table or view and
  return ordinary rows, so a graph traversal, a join, and an aggregation can
  live in one query over the same data — no separate graph database and no copy
  to keep in sync. The
  [ForceAtlas2 examples](./cugraph/algorithms/layout/cugraph_force_atlas2.mdx#examples)
  are a good place to start.
- **Vector search and vector ML _(in progress)_.** The next accelerator on the
  same pattern is [cuVS](https://github.com/NVIDIA/cuvs): `cuvs_*` table
  functions for GPU nearest-neighbor search and vector workloads such as
  clustering and dimensionality reduction, callable from SQL over your existing
  tables.
- **Lakehouse data access.** Query Iceberg tables from REST catalogs, AWS Glue,
  or S3-compatible object stores, with KvikIO streaming Parquet from object
  storage directly into GPU memory. Remote catalogs are read-only; views and
  scratch tables can live in an opt-in mutable local workspace overlay.
- **Explainable planning.** Planning reports record which parts of a plan ran on
  the GPU, which fell back to CPU, and the reason for each.
  [GPU coverage validation](./integration/gpu-coverage-validation.mdx) turns
  that into a question you can ask before a query runs:
  `SELECT * FROM nexus_explain_coverage('<sql>')` returns the verdict — which
  operator, expression, type, or source forces CPU execution — as
  machine-readable JSON. Errors cross the DataFusion boundary as typed values
  with stable identity rather than log text, a surface application code and
  agents can consume directly.
- **Bounded GPU memory.** Bounded mode plans each query against a GPU memory
  budget: shapes without a provable memory contract are rejected at planning
  time, and admitted queries receive their reservation before execution.
  Runtime memory pressure is absorbed by bounded chunk-split retries; a query
  that exhausts its retries fails with structured facts rather than an opaque
  OOM.

## Current limitations

- **A subset of Arrow data types.** Native execution covers the common
  relational types — booleans, integers, floats, `Decimal128`, strings, dates,
  timestamps, and durations. Nested and binary types and most list shapes stay
  on the DataFusion CPU path; on Iceberg scans an unsupported projected type
  fails planning instead. [Data Type Support](./reference/data-type-support.md)
  lists the exact boundaries.
- **No cross-GPU communication.** Independent queries can be placed on different
  GPUs, but a single query cannot exchange data between GPUs.
- **Partial Iceberg merge-on-read.** Position deletes are applied natively, but
  not on a fast path. Equality deletes and delete vectors are unsupported:
  because Iceberg scans have no built-in CPU reader, planning fails with a
  structured error even under the default `GpuPreferred` policy. Serving such
  tables on the CPU requires the opt-in `iceberg-cpu` build and the
  `cpu_fallback` session profile, which reroutes every Iceberg table in the
  session.
- **Parquet only.** Parquet is the only supported data file format for now.
- **No Substrait query-plan input.** Queries enter as SQL text, through an
  embedded DataFusion session or Flight SQL.

## Repository layout

The Cargo workspace has six packages:

- `datafusion-nexus` — the DataFusion-facing adapter: optimizer rule, table
  functions, Iceberg integration, the Flight SQL server, and reports.
- `nexus-query-engine` — the DataFusion-free native plan and GPU executor.
- `datafusion-nexus-workloads` — adapter-neutral TPC-H, TPC-DS, and ClickBench
  catalogs, fixtures, dataset discovery, and DataFusion registration.
- `datafusion-nexus-bench` — benchmark, report, triage, and stress binaries.
- `datafusion-nexus-tools` — developer and operator tools, including local
  end-to-end runners.
- `datafusion-nexus-examples` — runnable embedded-backend examples.

Two sibling repositories are also first-class parts of the implementation,
even though they are not workspace members: `cudf-rs` is the Rust/libcudf
boundary used by the native executor, and `cugraph-rs` is the Rust/libcugraph
boundary behind the `cugraph_*` SQL functions.
