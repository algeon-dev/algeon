# Algeon

**Algeon** is an experimental GPU query engine in which any SQL result can
feed a graph, vector, or machine-learning algorithm, and the algorithm's
output comes back as rows the same query can keep joining, filtering, and
aggregating. [Apache DataFusion](https://datafusion.apache.org/) is the first
integration: supported relational plans run on
[cuDF](https://docs.rapids.ai/api/cudf/stable/), while
[cuGraph](https://docs.nvidia.com/cugraph/latest/),
[cuVS](https://docs.nvidia.com/cuvs/home), and
[cuML](https://docs.nvidia.com/cuml/latest/) algorithms are SQL UDTFs
(user-defined table functions) whose relation arguments are ordinary
subqueries. You can embed the DataFusion adapter in a Rust application or
connect through Arrow Flight SQL.

The premise is that a relational query already reduces a lakehouse to a
working set of a few gigabytes, which fits on one GPU, and that the questions
worth asking about that working set (shortest paths, communities, nearest
neighbors, model scores) are the ones SQL alone handles badly. Algeon keeps
those questions inside the query and reports its planning decisions and
failures in structured terms a person or an agent can act on.
[Introducing Algeon](/blog/introducing-algeon) explains the reasoning.

GPU execution is opt-in per query: plans, or parts of plans, that Algeon does
not select for GPU execution stay on the normal DataFusion CPU path with the
same results. Once GPU execution starts, a failure is returned as a structured
error and is not re-run on CPU. Selection normally replaces a
[whole candidate](./design/native-lowering.mdx#selection-fallback-and-mixed-execution)
(with one certified
[mixed exception](./reference/glossary.md#planning-and-lowering)), and each
run executes inside a fixed GPU memory
[grant](./design/admission.mdx#device-profiles-and-grants).

DuckDB is the next narrow adapter direction and Spark is a longer-term
direction; neither is supported today.

## Where to start

- Build, then run a first query. Follow
  [Build & Test](./build/overview.md), then either embed Algeon in a
  [DataFusion session](./integration/datafusion-session.mdx) or start the
  [Flight SQL server](./integration/flight-sql-server.mdx) and connect with an
  ADBC client.
- See what runs on the GPU. Relational coverage is mapped in
  [Native SQL Support](./reference/native-sql-support.mdx); the algorithm
  UDTFs are documented in the [cuGraph](./cugraph/overview.mdx),
  [cuVS](./cuvs/overview.mdx), and [cuML](./cuml/overview.mdx) SQL APIs.
- Check a query before running it.
  [GPU coverage validation](./integration/gpu-coverage-validation.mdx)
  reports the planned execution path, and
  [Discover & Validate GPU UDTFs](./guides/gpu-function-discovery.mdx)
  validates an algorithm call without touching the GPU.

## Features

- Supported physical plans run on cuDF without changing your SQL, DataFrame
  code, or result format. You can require that a plan contain no CPU
  execution and have it rejected otherwise.
- `cugraph_*` UDTFs run 27 graph algorithms (BFS, PageRank, Louvain,
  ForceAtlas2, and more) over any edge relation. `cuvs_*` UDTFs run exact and
  approximate kNN, pairwise distance, KMeans, and PCA over vector columns.
  `cuml_*` UDTFs fit query-local models for decomposition, clustering,
  embedding, classification, and regression, and score rows with a pretrained
  forest. All of them return ordinary rows, and composed GPU stages pass data
  to each other without a host round trip.
- The [GPU UDTF catalog](./guides/gpu-function-discovery.mdx) lists the
  functions installed in a session, describes each contract, validates a call
  before execution, and reports whether each function is executable.
- GPU scans read local and S3-compatible Parquet. Remote sources are
  read-only, with an optional local workspace for views and scratch tables.
  Iceberg is not supported in this release; see
  [Iceberg support](./integration/overview.mdx#iceberg-support).
- [`algeon_explain_coverage`](./integration/gpu-coverage-validation.mdx)
  (or `EXPLAIN GPU` over Flight SQL) tells you which parts of a query will run
  on the GPU and why the rest will not. Errors carry stable machine-readable
  codes, kinds, and statuses.

## Current limitations

- A subset of SQL runs on the GPU. Unsupported operators, expressions, and
  Arrow types stay on the DataFusion path. See
  [Native SQL Support](./reference/native-sql-support.mdx) and
  [Data Type Support](./reference/data-type-support.md).
- One GPU per query. Independent queries can be spread across configured
  GPUs, but a single query never spans devices.
- No spilling. Each query runs inside the GPU memory cap it is granted, and
  exceeding it returns an allocation error; Algeon does not spill to host
  memory or disk in the style of
  [cuCascade](https://github.com/NVIDIA/cuCascade).
- Every algorithm call is query-local. Indexes, models, and graphs are built
  within one statement and released after it; there is no persistent
  artifact yet. The documented cuGraph, cuVS, and cuML functions are available
  when their Cargo features are enabled, and the
  [cuOpt SQL API](./cuopt/overview.mdx) remains work in progress.
- GPU file scans are Parquet-only. Non-Parquet files and other source types
  stay on the DataFusion path.
- Stability and verifiability both have a long way to go. APIs and query
  behavior may change incompatibly between releases, and the
  [benchmark page](./reference/benchmarks/index.mdx) states what has and has
  not been verified.
