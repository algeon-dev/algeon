# Fixtures

## `fixture/data/` — per-host benchmark data root

`fixture/data/` is the in-repo root for benchmark/workload Parquet fixtures
(TPC-H, TPC-DS, ClickBench, and graph demo datasets). Its contents are
**gitignored** — they are per-host local setup, never committed. Supported
fixture scripts and published docs refer to fixtures through
`./fixture/data/*`, so this directory is the single indirection point you
configure per machine.

### Expected layout

```
fixture/data/
  tpch/sf<N>/parquet/           # optimized Snappy Parquet, sorted row groups
  tpch/sf<N>/raw_parquet/       # optional raw tpchgen-rs output from --variant both
  tpcds/sf<N>/parquet/          # optimized Snappy Parquet, sorted row groups
  tpcds/sf<N>/raw_parquet/      # optional raw tpchgen-rs output from --variant both
  clickbench/hits.parquet       # single-file layout
  clickbench/partitioned/       # hits_0.parquet … hits_99.parquet
  demo/citation_network/v1/parquet/  # generated by fixture/scripts/dblp_ingest.py
```

### Generating TPC-H / TPC-DS

`fixture/scripts/gen_tpch.py` and `gen_tpcds.py` own the full lifecycle —
generation, layout optimization, and Parquet metadata verification — for each
dataset. Both use `~/code/tpchgen-rs` by default, write Snappy Parquet, use the
release `tpcgen-cli` build by default, and make `optimized` the default
`--variant`:

```bash
# Optimized SF1 and SF10 into the in-repo fixture roots:
fixture/scripts/fixture.sh tpch generate --scale 1 --scale 10 --force
fixture/scripts/fixture.sh tpcds generate --scale 1 --scale 10 --force

# Raw + optimized onto the NVMe mount the bench harness reads:
fixture/scripts/gen_tpch.py --scale 1 --scale 10 --variant both --out-root /opt/dlami/nvme/tpch --force
fixture/scripts/gen_tpcds.py --scale 1 --scale 10 --variant both --out-root /opt/dlami/nvme/tpcds --force
```

Both scripts drive `tpcgen-cli`: `gen_tpch.py` uses `tpcgen-cli tpch parquet`,
and `gen_tpcds.py` uses `tpcgen-cli tpcds parquet`. The shared optimizer rewrites
the final files as one Parquet file per table, sorted by workload-specific
pruning keys, with row-group statistics and Snappy compression. DuckDB is not
used to generate TPC rows; it only post-processes raw `tpcgen-cli` Parquet into
the benchmark layout. DuckDB is the default optimizer engine so large scales can
sort through its external temp storage; pass `--optimize-engine pyarrow` for the
older in-memory path.
Verification checks the expected table set, SF1/SF10/SF100 row counts, row-group
presence, compression, and monotonic row-group min/max for the leading sort key.
The files deliberately omit Parquet footer sorting-column metadata; the physical
row-group ordering is for pruning stats, not for advertising source output
ordering to DataFusion. Run either generator with `--help` for the full flag set
(compression, row-group target bytes, profile, threads, raw/optimized output).

### Fetching ClickBench

Use the unified fixture entrypoint for the official ClickBench Parquet layouts:

```bash
fixture/scripts/fixture.sh clickbench fetch --layout both --out ./fixture/data/clickbench
```

`--layout single` writes `hits.parquet`; `--layout partitioned` writes
`partitioned/hits_0.parquet` through `hits_99.parquet`; `--layout both` writes
both layouts.

### Generating the citation-network graph demo

`fixture/scripts/dblp_ingest.py` converts the DBLP / AMiner Citation
Network V12 JSON file into the five Parquet files used by the cuGraph SQL
examples. The upstream `dblp.v12.json` file is about 12.5 GB; keep
`fixture/data/demo` on NVMe with a symlink if the repository checkout is on
slower storage.

```bash
python3 fixture/scripts/dblp_ingest.py \
  --source-json /path/to/dblp.v12.json \
  --out-root fixture/data/demo \
  --overwrite
```

That writes `fixture/data/demo/citation_network/v1/parquet/` with:

- `edges_by_src.parquet`
- `edges_by_dst.parquet`
- `profiles_by_paper_id.parquet`
- `paper_authors.parquet`
- `paper_fos.parquet`

The local Iceberg REST loader can then register those files without rewriting
them:

```bash
docker compose -f fixture/iceberg-local/docker-compose.yml up -d
fixture/scripts/fixture.sh iceberg rest load \
  --workload citation_network \
  --load-mode add-files
```

`add-files` stages the Parquet files under `s3://lakehouse/staging/...` and
Iceberg references those staged files in place. Do not delete the staging prefix
while the REST fixture metadata is live. The REST fixture metadata is
ephemeral, so rerun the loader after every fresh `docker compose up`.

### Setting it up on a new host / for a new developer

Point each entry at wherever your fast local storage lives — a symlink is the
usual choice, but a real directory or a download target works too:

```bash
# Host with the AWS DLAMI NVMe drive staged at boot:
ln -s /opt/dlami/nvme/tpch       fixture/data/tpch
ln -s /opt/dlami/nvme/tpcds      fixture/data/tpcds
ln -s /opt/dlami/nvme/clickbench fixture/data/clickbench
ln -s /opt/dlami/nvme/demo       fixture/data/demo

# Host with data elsewhere — repoint the symlink, no code change needed:
ln -s /mnt/fastdisk/tpch fixture/data/tpch

# Or fetch/generate directly into these directories with the commands above.
```

### How the Rust bench harness resolves data (read before changing the defaults)

The Rust workload harness does **not** simply read `./fixture/data/*`. It keeps a
deliberate dual path (`crates/datafusion-nexus-bench/src/workload/*/dataset.rs`):

- When the physical NVMe mount `/opt/dlami/nvme` is present
  (`default_nvme_mount_present()`), it reads from the `DEFAULT_NVME_*` paths
  **directly**. This is required for GPUDirect-Storage (GDS) direct-device reads:
  `io_capability.rs` decides GDS eligibility by prefix-matching the source path
  against the physical mount root `DEFAULT_GDS_LOCAL_MOUNT_ROOT` (`/opt/dlami/nvme`).
- Otherwise it falls back to the in-repo `DEFAULT_LOCAL_* = ./fixture/data/*` roots.

On the DLAMI host the `fixture/data/*` symlinks above point at the same bytes, so
script-side (`./fixture/data/*`) and engine-side (`/opt/dlami/nvme/*`) access stay
consistent. **Do not** rewrite the `DEFAULT_NVME_*` data constants to
`./fixture/data` to "clean up" the literal: a relative, symlink-aliased path no
longer prefix-matches the GDS mount root and would silently disable direct-device
reads on the benchmark host. "Where is my data" (fixture discovery, host-agnostic)
and "is this path on a GDS-capable device" (physical classification) are separate
axes and are meant to stay separate.
